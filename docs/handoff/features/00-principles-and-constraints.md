## Purpose

This doc is the cross-cutting rulebook. The other area docs (01 to 11) describe subsystems; this one pulls out the rules the owner has imposed on *how a person interacts with code* in Doodle, so that a Rust IDE built from these docs keeps the same character: a controller in your hands, no typing of code, a cursor that hops between visible "dots", menus that only offer what fits where you are, and an app that is calm, predictable and replayable. Each principle below gives the rule, how Doodle actually implements it (checked against the code, not just the design docs), its edge cases, whether it is HARD (code enforces it or tests pin it) or SOFT (a convention or taste), the failure it prevents, and its evidence. Where the older docs say one thing and the code another, the code wins and the difference is called out. At the end of the Principles section is a list of superseded ideas so the Rust builder does not resurrect them by accident.

### P1. Projectional editing: code is built, never typed

- **Rule.** The document is a list of lines (nodes), each a sequence of fields (fixed text, editable names, typed holes). The user changes code only by: choosing from a menu at a dot or on a highlighted part (A, Y, LT+A), deleting a highlighted part (LT+B), moving a statement or block (Refactor > Grab / Copy line), or filling the *text* of a leaf (a name, a string's content, a comment's text, a number) by voice, by the LT+A text tools, or by the number keypad. There is no caret, no character-by-character insertion, and no keyboard typing into code.
- **In Doodle.** Keyboard keys are only stand-ins for pad buttons (src/app/main.odin `handle_key`: `w a s d`/arrows = d-pad, Return/Space = A, Backspace/Escape = B, `q`/`e` = LT/RT held, `x` / `y` = X / Y, `r` = RB, `t` = LB; Ctrl+C = copy). The only place typed characters are consumed is the Save-as / rename dialog's file-name box (src/app/save_dialog.odin `handle_save_input`; `Raw.typed` collects only `a`-`z`, `0`-`9`, `-` and `.`; Space types `_` there and Backspace deletes a character instead of cancelling). Note that `a s d w x y q e r t` are both pad stand-ins and typed letters; the dialog owns all input while open, so they only type. Files search takes no typed text at all (dictation only, see Open questions). The old free-text packages `src/buffer` and `src/editor` are dead stubs that `src/app` never imports.
- **Edge cases.** A loaded line the parser doesn't recognise is kept verbatim as fixed text: you can delete it or move it, not edit its characters (parse.odin header: "Recognized patterns have editable identifiers; the rest is fixed"). Inside a string or comment, "Edit word by word" steps over *words* with yellow dots in the gaps (src/model/word_edit.odin), still not characters.
- **Strength.** HARD: no code path writes keyboard text into the document.
- **Prevents.** The core mismatch UX.md §1 names ("a keyboard has ~100 discrete inputs; a gamepad has ~17"), syntax errors from typing, and the need for an on-screen code keyboard.
- **Evidence.** docs/EDITOR_MODEL.md opening block ("MAJOR DESIGN DECISION: Doodle is not a free-text code editor"); commits 5d2bea9 (first slice: "projectional editor, green-dot radial"), becfcc5 ("Doc is now a list of inserted text nodes"); src/app/main.odin `handle_key`, `Raw.typed`.

### P2. Gamepad-only authorable, proven by a real program

- **Rule.** Everything a real program needs must be reachable with the d-pad, A/B/X/Y and the two triggers (plus voice for names and text). The yardstick is an acceptance test that builds a real user program from New Project with controller-equivalent input only, then runs the compiler on the result.
- **In Doodle.** src/model/handmade_exact_build_test.odin builds the owner's Handmade Hero file (a win32 window: `package handmade`, `import win32 "core:sys/windows"`, constants, a `proc "system"` window callback with a multi-line parameter list, a `switch` over messages, `PatBlt`, a message loop) from an empty document. Rules of that test: every cursor move is a d-pad press through `update`; every menu pick moves the highlight with d-pad presses and confirms with A; Y = `change_selected`, LT+B = `delete_selected`, LT+A = `edit_selected` (keypad, text tools); dictation is `set_field_text` restricted to what push-to-talk can produce (lowercase snake_case names, spaced words); `WHITENESS`, `"WM_SIZE\n"`, `HandmadeHeroWindowClass`, the backticked `` `static DWORD Operation` `` and `TODO` in comments come from the LT+A text tools. Saving is `file_text`. Then `odin check` runs on it (the file goes to `<temp>/doodle_exact_build/main.odin`; with `DOODLE_ODIN`, else `C:/Odin/odin.exe` when it exists; otherwise skipped with `log.warn("odin check skipped (no DOODLE_ODIN)")`). Picking a grayed entry is logged as a soft finding (`FINDING: ...` warnings at the end), not a failure. The one deliberate deviation from the user's file is written in the test (`for win32.GetMessageW(...) > 0 {`).
- **Edge cases.** File names are the one thing where a keyboard helps; on the Deck the Steam on-screen keyboard (Steam + X) or dictation (hold X) covers it (README Deck table: "Doodle works without typing otherwise").
- **Strength.** HARD (acceptance test; also test_layout_handmade_from_empty_project, test_handmade_accept_build_program).
- **Prevents.** Features that only a keyboard can reach; "it parses but you can't build it" gaps.
- **Evidence.** EDITOR_MODEL.md §1.1 ("A complete, compilable program can be created without a keyboard"); handmade_exact_build_test.odin header.

### P3. Explicit insertion points: dots, and the colour vocabulary

- **Rule.** Every place something can be added is a visible dot that is a cursor stop. A on a dot opens the menu for exactly that place. Holes inside a construct are dots too, coloured by what they take, and labelled with the type they expect. After any insert, new dots appear wherever more can go.
- **In Doodle.** Colours (src/app/main.odin `slot_dot_color`, `draw_green_dot*`; src/app/editor_view.odin `COL_ATTR_DOT`, `COL_WORD_DOT`):

  | Dot | Colour | Meaning | A on it |
  |---|---|---|---|
  | Insertion dot in the gutter / between statements | quiet green (0.15, 0.60, 0.32); the focused one bigger and pulsing | a gap between top-level constructs or statements (insertion_points, body_dots) | Add menu at file scope, statement menu inside a body, member menu inside a struct/enum/union/bit_field body |
  | Attribute dot | purple (0.55, 0.22, 0.88), 14 px right of the declaration's first column (`ATTR_DOT_DX`, clear of the green dot), on the boundary above a file-scope proc (also one inside a file-scope `when`), above its `@(...)` lines if any; the d-pad stops on it between the green dot and the procedure | attributes of that procedure | Attributes menu (`test`, `private`, ...); the top-right hint reads `A: attributes  (test, private, ...)` |
  | `value` / `ret_more` | orange (1.00, 0.60, 0.15) | a value hole; `ret_more` = "another return value" | Fill slot (Number, String, Reference, Call, ...) |
  | `setup` and any other kind | neutral orange (0.95, 0.55, 0.20), the `slot_dot_color` default | e.g. the setup dot of an `if` / `switch` (`if ● x {`) | `Variable (:=)`, `Two names (:=)`, `Assignment`, `Call` (branch.odin `branch_slot_menu`) |
  | `type` / `variant` / `res_more` | blue (0.35, 0.70, 1.00) | a type hole; `res_more` = "another result"; `variant` = a type switch's case | `Type`, `Variable` (a `variant` dot: the union's variants, `nil`, `Type`, with variants other cases use grayed) |
  | `body` | green (0.35, 0.85, 0.45) | an empty statement line, shown as `●` | statement menu (in a struct / enum / union / bit_field body: the member menu) |
  | `args` / `fields` | bright green | optional "add another" (variadic argument, struct-literal field) | Fill slot / the fields not set yet |
  | `params` | violet (0.80, 0.45, 0.95) | add a parameter | `Add parameter` |
  | `capture` | pink | in front of a bare call that returns something | captures it: `● len(name)` -> `brave_otter := len(name)` |
  | word dot | yellow | a gap between words of a string/comment in word-by-word mode | Insert (format verbs, escapes, symbols) |

  Every slot dot pulses (main.odin `draw_colored_dot`), not only the focused one; green insertion dots are quiet except the focused one. Dots carry no text: a slot field has empty `text`, so it never reaches the saved file. Optional dots (`args`, `fields`, `res_more`, `ret_more`) are never saved; the `●` body line is dropped on save unless it is a block's only content (P4).
- **Edge cases.** One dot per gap: no dot between two blank lines, none between a blank line and a closing `}`, and no green dot next to an empty `●` statement line (that line already offers the same menu); no dots inside a `/* */` comment; inside a file-scope `when` the dots open the Add menu (declarations), not the statement menu, and the Add menu's `Dependencies` group is grayed there (src/model/body_dots.odin, ctrl.odin header and `ctrl_add_menu_opened`).
- **Strength.** HARD.
- **Prevents.** Hidden affordances; needing to know the grammar to know where code may go.
- **Evidence.** EDITOR_MODEL.md §2 and §2.1; commits 0801ab3 (slot dots), 5642695 ("color-code slot dots by kind"), 2d27703 ("Every green insertion dot is reachable"), 6a7a9c6 (insertion points); src/model/capture.odin, result_list.odin, attr_dots.odin headers.

### P4. Everything inserted has a default, and the document stays structurally valid (how far that really goes)

- **Rule.** Inserting any construct yields complete syntax at once: required names are filled with generated names, keywords and punctuation are fixed fields, and every remaining hole is a visible dot. No construct is ever half-typed.
- **Defaults in code.** `package main`; the first procedure in a file is `main`, later ones generated (commit 3b3fe59; "first" means no line of *this document* contains `:: proc` yet, sibling files are not consulted, see Open questions); Number -> `0`; String -> `""` with an empty editable text field (also `` `...` `` raw and `'...'` rune); `true` / `false` / `nil` fixed; a new project's file is `main.odin`; the project folder gets a random name. Builders: model.odin `append_proc_node`, `append_type_node`, `append_value_node`, `set_slot_literal`.
- **How far "compilable" really goes** (stated honestly; EDITOR_MODEL.md §1.2 says "valid Odin immediately", the code is more nuanced):
  1. Unfilled *structural* holes compile, thanks to `fixup_line` (src/model/serialize.odin, commit 17c7634): `( )` / `(  )` -> `()`, a `->` with nothing before `{` is dropped, trailing spaces trimmed. A fresh procedure
     ```odin
     main :: proc( ● ) -> ● {
         ●
     }
     ```
     saves as
     ```odin
     main :: proc() {

     }
     ```
  2. Optional dots are never saved: `-> (int, int●)` saves `-> (int, int)`; an untouched struct literal saves `T{}`; an unfilled variadic `args` dot disappears.
  3. Editor-only `●` statement lines are dropped on save when they sit next to real statements, but kept as the blank line when they are a block's only content, so empty bodies round-trip (`save_source`).
  4. Unfilled *required* value or type dots do **not** compile: they save as nothing (`BRAVE_OTTER ::`, `x :=`, `case :`, `a | ` operands). The loader turns them back into the same typed dots (parse.odin `open_value_line` / `open_value_to_dot`; commits 49a0a03, 7032779). The background `odin check` then shades those lines red with the compiler's message.
  So the real invariant is: *the saved file is always plain Odin text that reloads into exactly the same structure, and it compiles once every required dot is filled.*
- **Never invent references.** Generated names are only for *new declarations*. Reference picks an existing name from the file (`ref_candidates`: every editable name in scope except the package name, import aliases, string text and call names); Assignment asks for an already-declared target, never a `::` declaration (commit 4289c7d). With nothing to pick, `Reference` is grayed; picking it anyway starts a pick that ends at once (`start_ref_pick` -> `ref_pick_cancel`), so the dot simply stays empty. A fresh Assignment whose target pick finds nothing is taken away again with the notice `nothing declared to assign to here - declare it first (Declarations > Variable)` (src/model/ref_pick.odin `ref_pick_cancel`; B on that pick also takes the new line away, with the notice only when there was nothing to pick).
- **Strength.** HARD for structure and round-trip; SOFT for "compiles".
- **Prevents.** Half-typed syntax, empty required names, holes lost on reload, dangling references.
- **Evidence.** Tests test_serialize_empty_proc, test_fixup_line_empty_params, test_fixup_line_drop_arrow, test_load_empty_constant, test_load_empty_case, test_integration_reload_open_values, test_integration_reload_empty_operator_operands, test_format_keeps_statement_dots, test_empty_function_has_one_dot, test_reference_dimmed_without_names, test_assignment_cancel_takes_the_line_away.

### P5. Generated names: adjective_animal

- **Rule.** Every new declaration gets a fresh, readable, correctly-cased name, so the user never has to name something to proceed, and can rename later.
- **In Doodle.** src/model/namegen.odin: 20 adjectives (`brave calm clever swift quiet bright bold gentle lucky mighty nimble proud sly wise eager fuzzy jolly keen merry spry`) x 20 animals (`otter lynx finch heron bison gecko panda raven tapir koala moose quail viper wren yak zebra crane ferret hare ibis`). A deterministic counter `App.name_counter` picks adjective `counter % 20`, animal `(counter / 20) % 20`, and advances past any name already used (`is_name_used`: the exact text of an *editable* field anywhere in the document, or the name of a sibling file's procedure or type; sibling constants and globals are not checked). The counter is shared by all three casings and only ever grows. Casing by role: `generate_ident` -> `brave_otter` (procedures, variables, parameters, loop variables, labels, struct and bit_field fields, captured results, globals), `generate_type` -> `BraveOtter` (structs, enums, unions, other type declarations, and enum *members*), `generate_const` -> `BRAVE_OTTER` (constants, typed constants, `#config` constants). Project folders use a *random* `adjective-animal-NNNN` from a different, larger word list (src/app/save.odin `gen_project_name`: 24 adjectives such as `swift deep cool`, 23 animals such as `fox wolf dolphin`, a 4-digit number, e.g. `swift-fox-1234`; the value is recorded in traces as `str project_name`).
- **Renaming.** Dictate over the name (snake_case), or LT+A > Case. If the declaration has uses in scope, a menu titled `Rename brave_otter to window_title?` offers `Rename all 3 uses` (or `Rename the other use` when there is exactly one; at baseline that label renders as `Rename the other use%!(EXTRA 1)`, a format-string bug, doc 08 F19) and `Only this one` (src/model/rename.odin `rename_offer`). The new name is already in place when the menu opens; the menu only decides the uses. Scope of "all": file-scope declarations -> the whole file; parameters -> their procedure; loop / if / switch variables -> that block; other locals -> from the declaration to the end of their block. An inner redeclaration shadows (its uses are left alone); uses are whole words in code, not in strings or comments, not after a `.`, not a struct-literal field name. Choices in this menu are not recorded in the menu heatmap.
- **Edge cases.** The package name `main` and the first procedure `main` are not generated. EDITOR_MODEL.md §4 says collisions append `_2`; the code instead skips to the next counter value. With all 400 combinations of the requested casing in use, `generate_*` loops forever (gap, see Open questions). Because the check is exact text, `brave_otter` and `BraveOtter` do not collide with each other.
- **Strength.** HARD.
- **Prevents.** Blocking on naming (you cannot type), redeclaration clashes with sibling files.
- **Evidence.** Commit b8ecbb7; tests test_name_generator_uniqueness, test_name_generator_proc_snake_case, test_name_generator_type_pascal_case, test_name_generator_const_upper_snake, test_first_proc_is_main.

### P6. Menus offer what is valid at the spot; gray, don't hide, and say why

- **Rule.** The menu that opens depends on *where* you are, and inside it an option that makes sense in this kind of place but cannot apply right now is shown grayed rather than removed. Things that can never apply here are not listed at all.
- **Location decides the menu** (src/model/model.odin `update`, `open_add_menu`, `open_slot_menu`):
  - a green dot at file scope -> `Add  (insertion point)`: `File Setup`, `Dependencies`, `Procedures`, `Types`, `Values`, `Compile-time`, `Modifiers`;
  - a green dot or `●` line in a procedure body -> `Fill slot` statement menu, in this order: context entries first when they fit (`Else if`, plus `Else` unless the chain already has one, right after an if chain; `Case`, plus `Default case` unless the switch has one, at the end of a case clause; branch.odin `branch_extend_body_menu` prepends them), then `Declarations`, `Assignment`, `Calls`, `Branching`, `Loops`, `Jumps and cleanup`, `Error handling`, `Scope and blocks`, `Compile-time` (`#assert`, `When`), `Layout` (`Comment`, `Multi-line comment`, `Blank line`). Inside `Jumps and cleanup`, `Break <label>` / `Continue <label>` are added for the labels in scope, and `Fallthrough` is only kept at the end of a case clause that is not the last one (never in a type switch). Between `switch x {` and its first `case`, the whole menu is replaced by just `Case` / `Default case`;
  - a dot in a struct/enum/union/bit_field body -> members by kind (struct: `Field`, `Using field`; enum: `Member`, `Member = value`; union: `Variant`; bit_field: `Field`), plus the same `Layout` group (data_types.odin `types_slot_menu`);
  - a value dot -> `Number`, `String`, `true`, `false`, `nil`, `Reference`, `Call`, `Struct literal`, `Constant`, `Built-in constants`, `Enum value`, `Operator`, `Convert`, `Type`. `Built-in constants` and `Enum value` are always inserted after `Constant` (ctrl.odin `ctrl_extend_value_menu`; `Enum value` is grayed with the placeholder `(no enum type here)` when the dot expects no enum). Context additions: `Range` on a loop's iterable dot and on a case value dot; `Join with previous row` / `Own row` when Y refills an argument of a call laid out one argument per row (stmt_layout.odin `arg_row_extend_menu`); on a loop's iterable dot, non-iterable choices are grayed;
  - a type dot -> `Type` (imports' types as `win.` groups, `Composite`, the struct's `$T` params, this document's and the sibling files' types, basic types) and `Variable`. Special type dots: `bit_set[●]` -> the file's enums, `0..<N range`, `Type`; a bit_field's backing type -> `Type` with non-integers grayed; a polymorphic struct's params dot -> `Type param`, `Value param`.
- **The gray-versus-hide line, as the code draws it:**
  - *Hidden* (can never apply to this kind of place or this machine): packages for another OS (`make_view` -> `platform_ok`), `base:builtin` (not importable), attributes not valid for this declaration kind or not allowed on locals (src/model/modifiers.odin `attr_options`).
  - *Grayed, refused*: only in three kinds of *option* menus, the ones Y (or a modifier pick, or the purple dot) opens on a keyword or declaration. The option exists for this kind of thing but not for this instance. Choosing one does nothing and the menu stays open; it also leaves no heat (heat.odin `heat_is_action`). The code paths: ctrl.odin `ctrl_menu_choose` (`if e.dim do return // not possible here`), loops.odin `loop_option_choose`, branch.odin `branch_fill` (only for `BR_OPT_FILL`). Examples:
    - attributes / directives / calling convention (ctrl.odin, modifiers.odin): an attribute already present; `require_results` on a procedure with no results; `init` / `fini` on one with parameters *or* results; `test` on a procedure of the wrong shape; `#packed` when `#align` is there and `#align(N)` when `#packed` is (and either one when already present);
    - loop Y options (loops.odin): `Remove label` when that would change what a `break` / `continue` leaves; `Add #reverse` over a range, a map or a value the resolver says isn't iterable (`Iter_Kind.None`; an unresolved iterable stays allowed); `Add #unroll` over a slice, dynamic array, map, non-iterable value, a by-reference loop, or a range / string that isn't a constant expression (loop_unroll.odin); `By reference` when the loop has nothing to take by reference; on an assignment operator, the current operator and the operators the target's type can't take (`%=` on a float; assign_ops.odin `assign_op_fits`);
    - if / switch Y options (branch.odin): `Add else` when the chain already has an `else`; `Add default case` when the switch already has one.
  - *Grayed, advisory*: everything else that is gray still works when picked. menu_select has no general "dim" check: a grayed leaf is applied and a grayed group still opens. This covers:
    - type fit: fill options that cannot produce the dot's expected type (`true` for an `LPCWSTR` dot; typecheck.odin `apply_fit_dims`; a group is grayed when nothing inside fits). The menu title area says `expects LPCWSTR  -  grayed options don't fit` (main.odin `draw_radial`; shown whenever the dot has a type hint, `..T` for a variadic dot). These count as real uses for the heatmap (heat.odin: "Leaves grayed by type fitting still work when picked"), because the type resolver is partial. A dot whose type it can't resolve (`Unknown`), or that takes `any`, grays nothing;
    - context grays that `odin check` would then reject: `Break` outside a loop or switch, `Continue` outside a loop (loops.odin `loop_extend_body_menu`); case values another `case` of the same switch already uses, and union variants another type-switch case uses (branch.odin `dim_used`, `branch_slot_menu`); the Add menu's `Dependencies` group inside a file-scope `when` (ctrl.odin `ctrl_add_menu_opened`; the group still opens and its imports still insert); calls in a `when` condition (when_const.odin); names of the wrong type when picking an assignment target (assign_ops.odin `assign_target_dims`); `&name` in a loop iterable's `Pass as`;
    - the special case `Reference` with no names to pick: picking it ends the pick at once and nothing changes (P4).
  - *Empty groups explain themselves* with a dimmed placeholder leaf that does nothing when picked: `(no procedures defined)`, `(no imports yet)`, `(no imported constants)`, `(no enum type here)`, `(all fields set)`, `(fields unknown)`, `(no struct types)`. The main menu shows `Open Folder` dimmed (A on it does nothing). The footer `D-pad / Arrows to move    A / Enter to select    (Open Folder not wired yet)` is drawn, but at 1280x800 the HUD covers it (see the screenshots).
  - *Hidden although it fits the place*: the statement menu's context entries are added only when they apply, so they are hidden rather than grayed when they don't: `Else` when the if chain already has one, `Default case` when the switch has one, `Fallthrough` except at the end of a non-final case clause. The Y option menus show the same two (`Add else`, `Add default case`) grayed instead. The rule "gray, don't hide" is therefore followed in option menus and type fits, not everywhere.
- **Reasons.** The Key Layout picker gives a reason per grayed choice (`needs a trigger`, `face buttons only`, `would push Talk to RT+Down`, `Delete needs this button`, `fixed`, `not here`), repeats the long form under the title in warning colour, and explains a refused press on the status line (`Talk needs a face button (the d-pad splits words while you talk)`, `Walking needs a trigger (the highlight follows it)`, `Can't swap: ...`). Code menus give the *type* reason in the header line only; refused and advisory grays in code menus show no per-entry reason (gap).
- **Strength.** HARD for the location dispatch and for each gray and refusal the tests pin; SOFT for "gray, don't hide" as a general rule (exceptions above).
- **Prevents.** Invalid code; users hunting for an option that vanished; "why can't I?" with no answer.
- **Evidence.** src/model/typecheck.odin `apply_fit_dims`; heat.odin `heat_is_action`; model.odin `menu_select` (no general dim check); EDITOR_MODEL.md §2.1 ("impossible ones are grayed"); commits 2d27703, 465ce66; tests test_constants_and_operators_are_grayed_by_type, test_lptext_grays_out_bool_and_number, test_println_any_grays_nothing, test_attr_test_dimmed_for_non_test_shapes, test_imports_dimmed_inside_when, test_heat_dim_refused_options_record_nothing.

### P7. Type-aware everywhere (and humble about it)

- **Rule.** Menus react to the code underneath: every value dot knows the type it expects, and that knowledge drives graying, ordering and what gets written.
- **In Doodle.** A slot field carries `hint` (type text) and `hint_pkg` (the import path it's written in), set from call signatures (one dot per required parameter, labelled with its type), declared types, struct fields, the other side of a comparison, the switched value, the procedure's result types (return dots), map key types, enumerated-array indices. Uses: gray what can't fit (P6); pin the expected type first in `Convert` and `Struct literal`; gray the compound-assignment operators the target can't take (`%=` on a float; refused in Y's operator menu, advisory when picking the target of `● %= ●`; src/model/assign_ops.odin); `Field of p` with fitting fields lit; `&name` when a pointer is expected; `T(name)` conversions in `Pass as`; `Enum value` from the expected enum (or bit_set element: `{.VIDEO}`). Types written into code are qualified for *this* file: `Maybe(^sdl3.FRect)`, not `sdl3.Maybe(^FRect)` (commit f17d2dd). Knowledge sources: generated tables from the installed toolchain, the open document, and the sibling files (details: doc 06, doc 07).
- **Humility.** Resolution is categorical (`Type_Cat`: Unknown, Any, Integer, Float, Rune, Bool, String, CString, CString16, Pointer, Slice, Array, Map, Proc, Struct, Enum, Union, BitSet, Typeid, Multi), follows aliases and `distinct` down to a builtin (`LPCWSTR -> wstring -> cstring16`), applies Odin's untyped-constant rules to literals (`"..."` fits `cstring16`, `true` fits `BOOL :: distinct b32`), and matches calls by return type (distinct types by name). A slot it can't resolve is `Unknown` and grays nothing; an `any` slot grays nothing either (typecheck.odin header; open_slot_menu skips `apply_fit_dims` for `Unknown`).
- **Strength.** HARD for "Unknown never grays"; SOFT for completeness.
- **Prevents.** Offering choices that won't compile; and, just as important, blocking a correct choice because the resolver didn't understand something.
- **Evidence.** typecheck.odin, var_types.odin, calls.odin headers; tests test_messageboxw_dots_know_their_types, test_hwnd_and_uint_slots, test_fix_assign_ops, test_type_text_here.

### P8. Loaded source round-trips, into the same structure the menus build

- **Rule.** Opening a file must never change it except by formatting, and must produce exactly the fields the menus would have built, so loaded code is edited the same way as code built in Doodle. Lines the loader doesn't recognise stay as fixed text, never dropped.
- **In Doodle.** `doc_from_source` (src/model/parse.odin) is line-based and pragmatic, not a full parser. Every node's fields concatenate back to exactly the source line, so `doc_to_source(doc_from_source(s)) == s` for well-formed input (branch_parse.odin, loop_parse.odin, ctrl_parse.odin headers say this in the same words). A call written one argument per line is joined into one node and comes back in Doodle's one-argument-per-row format. Empty arguments and missing required arguments come back as typed dots. The open file keeps "no final newline" if it had none.
  On open, the app also runs `format_doc` (src/app/filenav.odin `filenav_load`): indentation, blank-line rules, one-line blocks split onto their own lines (block_split.odin). `format_doc` must be idempotent on already-formatted code, its output must load back to itself, and both must pass `odin check` (test_accept_one_liners_round_trip).
- **Edge cases.** CRLF input is read as LF (`\r` stripped) and saved as LF. Unformatted files are reformatted on save. Loaded constructs are structured: `x: T = v` splits out ` = ` so Y refills the value with a dot expecting T (commit 4289c7d); imports' paths are their own stop (49a0a03).
- **Strength.** HARD.
- **Prevents.** An editor that corrupts files it only half understands; two classes of code (menu-built vs loaded) with different editing powers.
- **Evidence.** data_types.odin header ("The loader ... produces exactly what the menus build, so loaded code is edited the same way"); commit 29c9b5f, 49a0a03 ("imports, constants and empty cases load as the menus build them"); tests test_parse_round_trip, test_accept_every_example_round_trip, test_handmade_accept_load_verbatim, test_handmade_exact_load_round_trip, test_decl_value_loads_and_saves_unchanged, test_load_type_decls_round_trip, test_loops_load_round_trip, test_one_arg_per_line_round_trip.

### P9. B / cancel restores exactly: one step back

- **Rule.** B undoes exactly the step in progress and nothing more; after B the document is what it was before the step started. Exploring a menu must be free.
- **In Doodle** (src/model/model.odin `menu_cancel`; the helpers it calls):

  | Where | B does |
  |---|---|
  | inside a menu | pop one level |
  | at a menu's root | close it; LT+A edit: nothing replaced; Y on an argument: its original fields are put back (`refill_restore`); A on a green dot in a body: the temporary `●` line is removed and a reused blank line restored (`body_insert_cancel`); Y on a call name: unchanged |
  | picking a name for `Reference` | the dot stays empty (or the refilled argument comes back) |
  | the `Pass as` menu | back to picking the name |
  | picking the target of a just-added Assignment | the new line is taken away |
  | modifier options opened from a modifier pick | back to picking the declaration |
  | picking the declaration for a modifier (Add > Modifiers > ...) | cancel the pick, nothing added |
  | `Declare as` (Y on a declaration's operator: `name := value   (type inferred)`, `name: type = value   (choose the type)`, `name :: value   (constant)`) | close, the declaration unchanged |
  | Grab / Copy line | every move undone exactly (a log of moves plus the original indent); for a copy, no copy |
  | word by word | leave, back to the whole field |
  | LT+A text tools | close without a change |
  | `Rename X to Y?` | same as `Only this one`: your edit stays, the other uses are untouched |
  | plain B in the editor | back to the main menu (`Back` hint: "back to the main menu (and out of menus)") |
  | B on the main menu | quit at once, no prompt (model.odin `update`, `.Menu`: it reads the raw cancel edge, so LT+B or RT+B there quits too) |
- **Exceptions at baseline (where B does *not* restore; the other docs pin them).** (1) `Declare as` > `name: type = value   (choose the type)` rewrites the line *before* opening the Type menu, so B in that Type menu leaves the new type dot: `x := 5` -> `x: ● = 5` (change.odin `apply_decl_form` inserts the dot and returns; `menu_cancel` has no restore for it; doc 02 §18 row 7, probe). (2) The `Number` keypad edits the number live, so B closes it and keeps every key already pressed (expr.odin `keypad_apply`; doc 08 F18). (3) The rename prompt's B keeps the declaration's new name (the edit already happened; only the other uses are left alone). (4) Dictation and text-tool choices have no B at all: they apply when the words arrive / the leaf is picked. A port should either make (1) and (2) restore, or treat them as intended and say so; nothing in code or commits states intent.
- **Edge cases.** There is no undo history beyond this: LT+B deletions are immediate (gap). B from the editor keeps the document in memory, but the main menu has no way back to it (New Project resets it, Recent Projects loads from disk), so editor B then main-menu B quits with unsaved edits silently dropped (Open questions 2).
- **Strength.** HARD.
- **Prevents.** Fear of exploring; half-applied edits after a cancelled menu.
- **Evidence.** Tests test_y_on_argument_refills_and_cancel_restores, test_reference_cancel_leaves_dot_empty, test_body_dot_inside_nested_block_and_cancel, test_grab_cancel_puts_it_back, test_copy_line_cancel, test_review_change_condition_cancel, test_capture_dots_resume_after_cancelled_edit, test_ide_menu_cancel_returns, test_menu_cancel_quits.

### P10. A few verbs that mean the same thing everywhere

- **Rule.** A small, fixed set of verbs applies to every kind of highlighted part, so learning one construct teaches them all.
- **In Doodle** (default layout, src/model/keymap.odin `KEYMAP_DEFAULT`, `ACTION_INFO` hints): A = add at a dot / fill a hole; Y = Change the highlighted part (a call's name: another procedure from the same package with the arguments kept; an argument or operand: refill it, B puts the original back; a dot: same as A; a type or an import: same as LT+A; a declaration's operator: `Declare as`; a string: its text tools with `Replace value` and `Edit word by word`; a keyword: its options such as `Add else if` / `Make #partial` / `Add #unroll`); LT+B = Delete it; LT+A = Edit its value (number keypad, text tools on names/strings/comments, type menu on a type, import menu on an import); LT+Y = Docs for it; RT+d-pad = walk the code tree (previous / next / in / out); RT+X = Refactor (Grab, Copy line); RT+A = Copy; hold LT+X = Talk into it. Keywords are selectable fields (`kw`) precisely so Y and LT+B can act on them (branch.odin, ctrl.odin headers).
- **Edge cases.** Two short-lived modes reinterpret the buttons: Grab (X or A drops, B puts back, the Walk previous/next buttons jump) and word by word (A, RT+X or plain Y change a word or insert at a yellow dot; RT+B or Delete removes a word; B leaves). Their hints name the default buttons literally (`A change   RT+B delete   B done`, `A insert   LT+X say words   B done`) and are not rewritten for a custom layout.
- **Strength.** SOFT (a design convention, consistently applied).
- **Prevents.** Per-construct special controls; memorisation.
- **Evidence.** src/model/change.odin header; ctrl.odin, branch.odin, loops.odin headers (each lists what Y and LT+B do on each keyword).

### P11. Deletion is structural and graduated; confirm only what Doodle can't take back

- **Rule.** LT+B deletes the highlighted *unit*, and the smallest meaningful one. Inside the document there is no confirmation; outside it (files, settings), destructive actions ask.
- **In Doodle** (`delete_selected` tries finer deletes first): a filled operand becomes a dot again; LT+B on that dot collapses the whole operator / ternary / conversion into one dot (in a chain of 3+ operands only that operand and one operator go); LT+B on a conversion's type unwraps the value; one name of `x, y: f32`; a result or a return value with its `, `; an `else` branch; a case value; an attribute, directive or calling convention; a captured name (the call stays); a struct-literal field; a loop header's part (label, `#reverse`, 2nd variable, a C-style init / condition / post); a `$T` parameter or a member of a one-line `enum { A, B }`; the `= ●` of a typed declaration; one line of a `/* */` comment (on a marker, or on its last line: the whole comment); a declaration together with its attribute lines; a block header deletes that statement's block, never the enclosing procedure (block_delete.odin); at file scope the whole construct; otherwise the single line. On a plain green dot it does nothing (except next to a blank line, where it deletes the blank line); on the "another result/value" dots it does nothing. On the only dot of a `return` with no value (`return ●`) it deletes the statement. The order of these checks is `delete_selected`'s: finer deletes are tried first.
  Confirmations exist only for: deleting a file or folder in Files (LT+B there; `Delete main.odin ?` / `Delete folder x/ ?`, `A delete    B keep it`; Recycle Bin on Windows, permanent on Linux even though the dialog text still says Recycle Bin), saving over a *different* existing file (a second A), removing an added projects folder (X twice: `press X again to remove it from the list (the folder stays on disk)`), resetting the key layout (`Reset every button?`, `A reset        B keep`). Quitting (main-menu B, IDE menu > `Exit`, closing the window) never asks.
- **Strength.** HARD for the graduated deletes (tests); SOFT for the confirmation policy.
- **Prevents.** One press wiping a whole procedure; dialogs interrupting flow for reversible-feeling edits.
- **Evidence.** model.odin `delete_selected`; expr.odin, result_list.odin, data_member_edit.odin headers; tests test_delete_on_dot_is_noop, test_delete_selected_block_header_deletes_whole_block, test_fix_chain_dot_delete, test_delete_one_of_several_names, test_delete_bare_return, test_review_delete_shared_member_names.

### P12. Sibling files are read-only; edits never leave the open file

- **Rule.** Other files of the package are read to type the code and fill the menus, but Doodle never writes them. Every edit, rename and generated name concerns only the open file.
- **In Doodle.** src/model/siblings.odin: an Odin package is a folder, so the other files' file-scope names are usable without an import. Procedures (signature lines), file-scope types (parsed with the editor's own parser, kept as text) and imports of the `.odin` files next to the open one are loaded when the open file changes or is saved, or the project folder changes (src/app/save.odin `refresh_siblings`; never per frame); only files whose size or modification time changed are re-parsed; files over 1 MB (`SIBLING_MAX_BYTES`) are skipped. Sibling constants and globals are not loaded. No node index ever points into a sibling: only names and text are kept. `@(private="file")` declarations and files tagged `#+private file` are invisible; package-private ones are visible. The open file's own declarations shadow same-named sibling ones. Rename: "Other files of the package are not changed" (rename.odin). Generated names avoid sibling procedure and type names (`is_name_used`). Inside the project, the app writes only the open file (Save / Save as / before a Run), files and folders the user creates, renames or deletes in Files, and `.doodle/run.txt` / `run.log`; elsewhere it writes the per-user files next to the exe, the background check's scratch copy (a temp folder), Setup's installs (Odin, clang wrappers, stb libraries, self-update), a PATH entry for vendor libraries when the user picks `Add to my PATH (permanently)` / `Add to my library path (~/.profile)`, and debug trace recordings. The model package writes nothing (P25).
- **Strength.** HARD.
- **Prevents.** Silent multi-file edits you can't review on a 7-inch screen; redeclaration errors.
- **Evidence.** EDITOR_MODEL.md §3.4 "The package's other files"; tests test_sibling_types_listed_after_own, test_sibling_type_shadowed_by_own, test_sibling_private_types_hidden, test_sibling_huge_source_skipped, test_load_siblings_reuses_unchanged_files.

### P13. The HUD always shows what each button does now; every screen names its controls

- **Rule.** Never make the user guess. The bottom HUD is drawn from the live button layout every frame, and every other screen states its own controls in plain words.
- **In Doodle.** src/app/main.odin `draw_hud` / `draw_bank` / `slot_glyph`: three banks (`L-TRIGGER`, `DEFAULT`, `R-TRIGGER`); the active bank (LT held -> left, RT held -> right, neither -> middle; both held -> LT wins, `active_bank`) is drawn at scale 1.15 with its label in green ink, the others at 0.82 and half alpha. Each slot shows the bound action's icon (Talk speech bubble, Delete trash can, Save and Save as floppy, Files folder, Copy, Select add, Back) or its ASCII glyph (`ACTION_INFO.glyph`: Edit `e`, Change `*`, Docs `?`, Run list `>`, Refactor `G`, IDE menu `=`, ...); an unbound face button shows its own letter; an unbound d-pad arm is blank (it still moves the cursor), and so is a walk on its own RT arrow (`walk_natural`; in the LT bank a walk shows its glyph, because a blank arm there means "unbound"). Talk's button pulses green only when talking would start right now (a dictatable field is highlighted, speech-to-text exists, no overlay). Context hints at the top right (`Y: add else / else when, change condition    LT+B: delete`) are rewritten for the current layout by `rebind_hint`, which drops a segment whose action has no button. Menus show `n / N     D-pad move   + select   < back`, a breadcrumb of the menus passed through (`Fill slot  >  Type  >  win.  >`, trimmed from the left with `..` when too long), `^ more` / `v more` when the grid scrolls, the full label of a truncated highlighted cell under the grid, and the `expects T` line. Pick modes show a yellow banner under the title bar (`Pick a name to reference   -   D-pad move   A use it   B cancel`; `Pick a declaration for the attribute   -   D-pad Up/Down move   A choose   B cancel`, with `a struct for the directive` / `a procedure for the calling convention`); Grab replaces the top-right hint with `Up/Down move   RT+Up/Down jump   X / A drop   B put back` (`... B no copy` for a copy; `Outside a procedure: can't drop here   Up/Down move   B no copy` where a copy can't land). Every overlay has a footer (Recent Projects `n / N     D-pad move   A open   B back`, Run list `D-pad move   A select   Y favorite   B back`, Settings `D-pad move   A switch / install   B back`, Files `D-pad move   A open / drop in   B back   X new file   LT+X rename   LT+B delete   Y search   RT+B prev file`, with `B up a level` after dropping into a folder, wrapped onto more lines in a narrow window, ...). The Key Layout page previews the bank under its cursor in the HUD and says what the highlighted button does (`LT+B: Delete  -  delete the highlighted part`; a locked slot: `B: fixed - always moves / selects / goes back`).
- **Edge cases.** The HUD is drawn unconditionally after every overlay from the editor keymap (main.odin main loop: `draw_hud(r, &m, hud_inp, w, h)`; only the Key Layout page substitutes its cursor's bank). So in overlays with fixed controls (Files, Run list, Save as, Docs, Settings, Recent Projects, New Project) the HUD keeps showing the editor layout while the buttons mean what the overlay's footer says (gap; verified from the code, not by running the app). Talk's glow is suppressed while any overlay is open. The Grab and word-by-word hints name default buttons and are not rewritten for a custom layout.
- **Strength.** HARD for the keymap-driven HUD; SOFT for full coverage.
- **Prevents.** Memorisation and guessing; UX.md Pillar A calls the HUD "the single most important affordance".
- **Evidence.** EDITOR_MODEL.md §5; keymap.odin `rebind_hint`; editor_view.odin banners.

### P14. A key layout can never lock you out

- **Rule.** Users may rebind 18 of the 24 bank slots, but no layout can make Doodle unusable.
- **In Doodle** (src/model/keymap.odin, keys_page.odin):
  1. Plain d-pad, A and B are fixed (`slot_locked`): they move, select and go back everywhere, menus included. Menus (`.Radial`) skip the keymap entirely and read only the d-pad / A / B edges, whatever trigger is held (so LT+B inside a menu is just "back"); X and Y do nothing there. A press on a locked slot of the Key Layout page says `D-pad, A and B (no trigger) always move, select and go back`.
  2. The Key Layout page's own controls are fixed, never read from the keymap.
  3. `Delete`, `Files` and `Save` are `required`: always exactly one button; clearing or overwriting their button is refused (`Delete needs a button: give it another one first`).
  4. One button per action: assigning an action that is already elsewhere *swaps* the two slots (the moved row flashes `moved`; the status names both buttons: `Talk moved to LT+Y`, or `Docs moved from RT+A to X` when the slot was empty). A swap is refused when the displaced action may not go to the other slot (`Can't swap: ...`).
  5. Overwriting a non-required action can leave it without a button; the status says so (`LT+X: Format file  -  Talk has no button now`).
  6. `Talk` must be on a face button (`face_only`: d-pad Down splits words while talking). Walks must be on a trigger bank (`trigger_only`: the highlight follows the held trigger).
  7. In the editor, an unbound trigger + face button does nothing; it never falls through to the plain button (a cleared LT+B must not act as B and drop you to the main menu; keymap.odin `keymap_resolve`). An unbound trigger + d-pad still moves the cursor. Exception (from code reading, no test): on the main menu the model reads the raw B edge, so LT+B / RT+B there quit like plain B.
  8. LB (Run tests) and RB (Run favorite) are fixed shortcuts outside the layout (and Ctrl+C copies); they act only in the editor with no overlay open, nothing being dictated and no Reference / modifier pick running. Run tests and Run favorite can additionally be placed on a bank slot. The IDE menu action (default LT+Left; `Format file`, `Key layout`, `Exit`) works from the main menu too (model.odin `update`: "global: the main menu too").
  9. The file is repaired on load (locked slots reset, impossible or duplicate actions dropped, missing required actions re-homed); a newer or unreadable file is never overwritten and the defaults are used.
- **Doc vs code.** EDITOR_MODEL.md §5 says "Delete, Save as and Files always have a button"; the code makes `Save` required, and `Save as` has no default button (test_keymap_old_save_as_layout).
- **Strength.** HARD.
- **Prevents.** Bricking the app with a bad layout, a hand-edited file, or a downgrade.
- **Evidence.** Tests test_keymap_assign_rules, test_keymap_parse_repairs, test_keymap_resolve, test_keys_page_refusals, test_keys_page_events_name_what_was_lost, test_keys_page_refused_swap_names_the_pick; commit 2d27703 ("LT+B no longer also jumps to the main menu").

### P15. One press, one meaning; whoever is on top owns the input

- **Rule.** Each press is handled once, by exactly one owner, and modal states swallow everything that isn't theirs.
- **In Doodle** (src/app/main.odin main loop): the topmost overlay owns all input, in this order: stb-build prompt, vendor-library prompt, Save-as/rename dialog, Files, Key Layout, Settings, Recent Projects, New Project, Docs panel, Run list, then the editor/menus. Edges consumed by a trigger combo or an overlay never leak into the editor (commit 2d27703). At most one overlay opens per frame (`app_requests`). A Talk press made while any overlay is open belongs to the overlay (e.g. Talk on plain Y, and Y closes the Docs panel) and can't start dictation until it is released and pressed again (`g_talk_stale`). While dictating, navigation is masked (d-pad Down marks a word boundary; held-d-pad repeat is off), and until the background transcription is in (`g_stt_busy`) the editor receives no presses at all, so the words land in the field that was highlighted when recording began. While something is grabbed, or while editing word by word, every other button is ignored and the hint shows only the live controls.
- **Strength.** HARD.
- **Prevents.** Double actions, accidental quits, dictation landing in the wrong field.
- **Evidence.** keymap.odin `keymap_resolve` comment; grab.odin and word_edit.odin headers.

### P16. Voice is for single words and short text, never commands or code

- **Rule.** Speech fills one leaf at a time. It is not a command language and never produces syntax.
- **In Doodle.** Hold Talk (default LT+X). The mic is offered only when the highlighted part can take speech (src/model/dictation.odin `dictation_target`): a name (any editable field that isn't a string's or comment's text) -> `Identifier` (lowercase snake_case; words joined with `_`; pressing d-pad Down while holding starts a new word; each `_`-separated piece of 3+ letters is snapped to the document's editable names or a fixed list of common Odin words at edit distance <= 1, e.g. "maine" -> `main` (src/stt/stt.odin `snap_identifier`, model.odin `collect_vocab`; not scope-aware), with a Whisper prompt `lowercase Odin code identifiers: ...` built from the same list), a string's or comment's text -> `Free_Text` (spaces kept), a number literal or a value dot that takes a number -> `Number` ("twenty five" -> `25`, "three point five" -> `3.5`, "minus two" -> `-2`; otherwise the status `Heard "x" - not a number`). Local whisper.cpp only, no cloud. Feedback: `[REC]` while holding, cycling `transcribing...` while the words are worked out on a worker thread (the editor waits and the words go to the field captured when recording began), then `heard: x`. A name change goes through rename (P5). What voice can't say is covered by LT+A text tools (on a name: Case > `snake_case`, `UPPER_SNAKE`, `Ada_Case`, `camelCase`, `PascalCase`; on a string's text: the same plus `Joined`, and Escape > `\n \t \r \0 \\ \"` appended; on a comment's text: Word case > a word > UPPER / Capitalized / lower, and Backticks > first word > last word; src/model/text_tools.odin), the number keypad (`1`-`9`, `0`, `A`-`F`, `0x`, `.`, `Del`, `OK`; keys that wouldn't change the number are grayed; expr.odin `NUM_KEYS`), and word-by-word inserts (format verbs, escapes, symbols). Voice also names files (Save as / rename: hold X) and searches Files (hold X); those overlays use the physical X button whatever Talk is bound to, and they wait for the words instead of transcribing in the background.
- **Strength.** HARD for the gating; SOFT for "short".
- **Prevents.** Unreliable recognition of punctuation and syntax; cloud dependence; a mic that listens when nothing can take the words.
- **Evidence.** docs/STT.md ("not for sentences"); commits 3714653, 381af06, d73fe11 ("mic gated to editable fields only"), 76188d0 (free text for strings), d6d998b (background dictation); tests test_spoken_number, test_dictate_number_into_value_dot, test_word_edit_*.

### P17. Nothing changes without input (deterministic, replayable)

- **Rule.** Application state changes only in response to input; the same input stream replays to the same state, frame by frame.
- **In Doodle.** The model is a pure `update(App, Input)`. Held-d-pad auto-repeat (0.35 s delay, then every 0.07 s, about 14/s) is synthesised as ordinary press events in the platform layer, so it is recorded and replayed (src/platform/platform.odin `dpad_repeat_tick`, commit d6e415a). Generated identifiers are counter-based. Values a replay can't recompute are recorded as strings: the random project name and each speech-to-text result, tagged with the frame it arrived in. Background `odin check` results only shade lines and are left out of the state fingerprint. The file grid knows nothing of the window size ("a move comes out the same at any size"; file_grid.odin header). A replay runs one empty frame after each recorded one, "which is all the app ever needs, because nothing in Doodle changes without input" (docs/TRACE.md). New features keep old recordings valid: legacy flags restore the old main menu and New Project flow, and new state is mixed into the fingerprint only while the new feature is open.
- **Strength.** HARD (`tools/trace.py verify all` replays every recording and compares fingerprints).
- **Prevents.** Flaky behaviour, unreproducible bugs, UX research on unreliable data.
- **Evidence.** docs/TRACE.md; src/app/trace.odin `fingerprint`, `trace_stt_poll`.

### P18. Trace and replay are a UX research tool

- **Rule.** Every debug run is recorded so the owner can see what is slow or confusing to reach with a controller, then redesign it.
- **In Doodle.** Each debug run writes `bin/traces/<UTC stamp>/` (`input.log`, `events.jsonl`, `snapshot/`; newest 40 kept; a small red dot top-left while recording). `tools/trace.py report` shows button and combo use per screen, menu picks with their cost in presses, time per screen and mistake signals: `A then B (picked wrong?)`, `N+ B presses in a row`, `d-pad oscillation`, `delete then re-add`, `menu backed out without a pick`, `save dialog cancelled`, `repeated dictation`, plus ranked suggestions ("frequent and expensive"). `find` locates moments; `--replay ... --until F` jumps there; take over to continue live; `script` drives the UI with scripted presses and saves a screenshot. Replays run in a sandbox copy and never touch real files, programs, clipboard, sounds, Recycle Bin, heat, or the keys/roots/settings files. The harness is debug-only: release builds define `DOODLE_TRACE=false`, and CI fails if the release binary contains the string `doodle-trace 1`. Every hook is marked `TRACE hook` with the original code in its comment, so the harness can be removed.
- **Strength.** HARD (CI check, sandbox rules); SOFT (how it's used).
- **Prevents.** Designing controls by guesswork; shipping a recorder to users.
- **Evidence.** docs/TRACE.md; src/app/trace.odin header; .github/workflows/release-steamos.yml.

### P19. Persistence files: never overwrite what you can't read

- **Rule.** Small per-user files, tolerant to hand edits, versioned, and never destroyed by a Doodle that doesn't understand them.
- **In Doodle.**
  - Location: next to the executable (`heat_exe_dir`): `doodle_keys.tsv`, `doodle_heat.tsv`, `doodle_roots.txt`, `doodle_settings.txt`. Kept across self-updates (`KEEP_FILES` in src/app/updater.odin) and Deck reinstalls (tools/deck_install.sh).
  - First line: a versioned header `doodle-<kind> 1` (`doodle-keys 1`, `doodle-heat 1`, `doodle-roots 1`, `doodle-settings 1`; traces: `doodle-trace 1`).
  - Missing file: defaults, silently. A file with another header (a newer Doodle) or one that exists but can't be read: defaults are used and the file is **never** overwritten (`*_text_ok`, `g_*_nosave`); the problem is reported once per session on the status line. Failures never stop the editor.
  - Hand edits: blank lines and `#` comments skipped, garbage lines ignored, the keymap repaired; duplicates: keys file first one wins, heat counts of a repeated key add up, roots repeats (any case or slash style) dropped; unknown settings lines are kept and written back as they were (`#` lines in the settings file are dropped on the next save).
  - Stable identifiers: action keys in the keys file "never renamed once shipped"; enum order is internal; an old file picks up a new action's default slot.
  - Write safety: heat is saved at most every 2 s and at quit; a save re-reads the file, merges this session's pending uses (several Doodles may run), writes `<file>.tmp` and renames it over; on failure the uses stay pending and are retried. Keys, roots and settings save right after each change.
  - Replays pin all of them from the recording and never read or write the real files.
  - Project-local: `<project>/.doodle/run.txt` (run commands, one per line, `*` prefix = favorite) and `.doodle/run.log` (output when there is no terminal). `run.txt` has no versioned header (inconsistent; see Open questions).
- **Strength.** HARD (parse/serialize tests, `text_ok` tests).
- **Prevents.** Data loss on upgrade/downgrade or with two instances; a corrupt file locking the user out.
- **Evidence.** src/app/heat_store.odin, keys_store.odin, roots_store.odin, settings.odin headers; commits f544db5, df22753.

### P20. What you see is what gets saved

- **Rule.** The editor shows the file as it will be written: same line breaks, same indentation, same line numbers.
- **In Doodle.** A node is one logical line, but a call or struct literal longer than 80 columns (`MAX_COLS`, tabs count 4) is shown *and* saved one argument per row with trailing commas; the same row plan drives the view and `doc_to_source` (src/model/format.odin). The code font is sized so 80 columns fit the window (13 to 28 px; editor_view.odin). Gutter line numbers are the file's line numbers (`node_line_starts`; one nuance under Edge cases), so compiler messages line up. The only extras on screen are dots, expected-type labels, and soft-wrapping of rows that still don't fit. `format_doc` runs on load, on save and from IDE menu > `Format file` (also bindable as the `Format file` action).
- **Edge cases.** `node_line_starts` counts every node as `doc_to_source` writes it, editor-only `●` lines included (as blank lines), and the background `odin check` compiles that same text (src/app/checker.odin uses `doc_to_source`), so gutter numbers and compiler messages always agree. The saved file (`save_source`) drops a `●` line that sits next to real statements, so while such a line exists the lines below it are numbered one higher on screen than in the saved file.
- **Strength.** HARD.
- **Prevents.** Surprise diffs; compiler line numbers that don't match what you see.
- **Evidence.** format.odin and editor_view.odin headers; tests test_long_call_saved_one_arg_per_line, test_format_is_stable_and_collapses_blanks.

### P23. Menus remember you; big APIs stay findable

- **Rule.** Navigating thousands of library names with a d-pad must stay short, stable and familiar.
- **In Doodle.** Menus are square-ish grids (`grid_cols`: the smallest c with c*c >= n, at most 8 columns) with wrap-around at the edges; after the recent section, more than 12 remaining entries (`BUCKET_THRESHOLD`) sort alphabetically, 12 or fewer keep authored order (`make_view`). A `RECENTLY USED` section comes first (already-imported packages, recently used imports, and procs/types/constants already used in this file, pinned), then `ALL`; the captions only appear when there is something below the recent rows. Entries meant for another OS are filtered out here (`platform_ok`). Exception: the `Type` submenu of a value / type dot is pushed without `make_view` (no sorting, no recent section, no platform filter), so it keeps its order: imports' groups, `Composite`, `$T` params, this package's types, basic types. Large packages are grouped by source file, foreign block and name prefix (`MB_...`, `WM_...`); groups stay flat up to 60 and are split beyond that. Grouping is computed from the package's full list *before* this file's used names are pinned, so the trails don't depend on the file. A breadcrumb above the title shows where you are; a truncated highlighted label is shown in full below the grid; boxes size to their longest label (220 to 480 px).
- **Strength.** SOFT (tests pin layout and heat).
- **Prevents.** Re-learning menus per project; long d-pad trips.
- **Evidence.** model.odin `make_view`, menu_sections.odin, heat.odin; commits 8422cf0, 79a7b87, ccae370, bf5ec80, 63c2e8c.

### P24. Steam Deck is a first-class target

- **Rule.** Everything must work handheld, in Game Mode, at 1280x800, with no keyboard, no root, and no desktop setup.
- **In Doodle.** The window starts at 1280x800 (the Deck's native size; main.odin `WINDOW_W`, `WINDOW_H`). A font is bundled (DejaVu Sans Mono, so Linux / the Deck always has one; `load_a_font` tries an optional `assets/fonts/mono.ttf`, then Consolas / Segoe UI on Windows, then the bundled file). ### P25. Pure model, thin app

- **Rule.** All decisions live in a pure, unit-tested model driven by an abstract input; the app layer only translates devices, draws, and does I/O.

## Data model & formats

- **Field** (paraphrase of model.odin `Field`): `text`, `editable` (a name or leaf text the user can change), `slot` (a dot), `kind` (for slots: `params`, `type`, `value`, `body`, `args`, `fields`, `capture`, `res_more`, `ret_more`, `variant`, ...; for fixed or editable fields a role: `kw` keyword, `string`, `comment`, `decl` operator, `litkey`, `member`, ...), `hint` and `hint_pkg` (expected type and the import path it's written in). A **Node** is a line: an ordered list of fields whose texts concatenate to the source line. The **Doc** is a list of nodes plus `no_final_newline`. Doc 01 covers this in full.
- **Entry** (menu item) flags that carry principles: `dim` (grayed; whether a gray is refused depends on the entry's `fill` kind, P6), `pinned` (listed first as used in this file), `heat_key` (heat identity when the label isn't stable, e.g. an import path for an alias group), `platform` (comma list of OS names; filtered out elsewhere), `alias` (entering this group makes the next import aliased), and one behaviour (`children` submenu, `insert`, `import_path`, `keyword` + `ident_default`, `proc_outline`, `type_construct`, `value_construct`, `special`, `fill` with `call_name` / `call_pkg` arguments, `quit`, `format`, `key_layout`). A leaf with none of these is a placeholder and does nothing.
- **Input**: edges `confirm`, `cancel`, `up`, `down`, `left`, `right`, `x`, `y`; holds `lt_held`, `rt_held`. (LB/RB and Ctrl+C are handled by the app layer outside the layout.)

## Carrying this to Rust

**(a) What transfers unchanged.** Every principle above is language-agnostic: no typing of code; visible dots and their colour vocabulary; defaults and generated names (`brave_otter` for fns/locals/params/fields, `BraveOtter` for types/traits *and enum variants*, `BRAVE_OTTER` for consts/statics: Rust's naming lints (`non_snake_case`, `non_camel_case_types`, `non_upper_case_globals`) want exactly the casings Doodle already generates, including PascalCase enum members); references picked, never invented; menus chosen by location with gray-versus-hide; type-aware graying where `Unknown` never grays; exact round-trip and loader/menu symmetry; B restores exactly; graduated structural deletes; sibling files (other modules) read-only; the three-bank HUD drawn from a lock-out-proof keymap; one owner per press; voice only into leaves; determinism, trace/replay with sandbox and verify; persistence-file rules; WYSIWYG formatting; plain language; the paper/pencil feel; the Deck as reference platform; a pure model crate with an abstract `Input`; a north-star acceptance test that builds a real program from an empty project with controller-equivalent input, then compiles it.

**(b) Odin-specific pieces and their Rust analogs.**
- `when TRACE { ... } else { stubs }` with `#config(DOODLE_TRACE, ODIN_DEBUG)` (on in debug builds, overridable with `-define:DOODLE_TRACE=...`) -> compile the recorder under a cfg and give the other branch no-op stubs with the same signatures; keep the CI grep that fails if the release binary contains `doodle-trace 1`. Cargo features cannot be switched on per profile, so pick one of: (1) `#[cfg(all(debug_assertions, not(feature = "no-trace")))]` (on in `cargo build`, off in `--release`, with an opt-out feature); (2) a Cargo feature `trace` that dev scripts (`cargo xtask`, `just`) always pass; (3) a `build.rs` that reads the `PROFILE` env var and prints `cargo::rustc-cfg=trace` (declare it with `cargo::rustc-check-cfg=cfg(trace)` to avoid the unexpected-cfg lint), then gate with `#[cfg(trace)]`.
- `bit_set[Action]` (`Actions`, `Pad_Held`) -> the `enumset` crate (derive `EnumSetType` on the enum) or `bitflags`; enumerated arrays `[Pad_Button]Action`, `[BANKS][Pad_Button]Action` -> the `enum-map` crate (`EnumMap<PadButton, Action>`) or plain `[[Action; 8]; 3]` indexed by `button as usize` on a fieldless `#[repr(u8)]` enum.
- Static tables (`ACTION_INFO`, `KEYMAP_DEFAULT`, `ADJECTIVES`) -> `const`/`static` arrays or a `match` returning `&'static ActionInfo`.
- `union` / string `kind` tags on fields -> Rust `enum FieldKind { Value, Type, Body, Args, Fields, Params, Capture, ResMore, RetMore, Keyword, ... }`. Doodle's stringly typed kinds and `__fill__` markers are an Odin-era shortcut; use enums.
- `context.temp_allocator` + `free_all` per frame -> owned `String`s, or a per-frame arena (`bumpalo`) for layout; the borrow checker prevents the per-frame-memory-kept-too-long bug fixed in commit 7032779 and the project-path bug in 2d27703.
- `defer` -> `Drop` / scope guards; `or_return` -> `?`; procedure groups -> traits or generics; `distinct` -> newtypes; `#+build` and `when ODIN_OS` -> `#[cfg(target_os = ...)]`.
- Package = folder -> crate/module tree. The mapping is not one-to-one: Odin's sibling files share one namespace (a sibling's `Player` is usable as `Player`, no import), while each Rust file is its own module, so another module's item needs a path (`crate::world::Player`) or a `use`. Picking such an item must also add the `use` line (or write the path), as Doodle adds `import "core:testing"` when `test` needs it (see c).
- `odin check` -> `cargo check --message-format=json` (or rust-analyzer flycheck); `odin test .` -> `cargo test`; `odin run .` -> `cargo run`.
- Generated `core_*.odin` tables -> data from rust-analyzer over std and the `Cargo.toml` dependencies, or rustdoc JSON (`cargo +nightly rustdoc -- -Z unstable-options --output-format json`; nightly-only and its format is versioned, so pin it; std's own JSON ships as the nightly `rust-docs-json` rustup component), not hand lists. Doodle generates its tables offline from the installed toolchain (tools/gen_core_tree.py, gen_core_procs.py); a Rust IDE needs the equivalent per toolchain version and per dependency version from `Cargo.lock`.

**(c) Rust concepts Odin lacks, and how these principles extend to them.**
- **impl blocks and traits.** Inside `impl T { }` the dots offer associated fns, consts and types. `impl Trait for T` should add every required item at once, each with a default body. An empty body of a fn that returns a value does not type-check, so prefill unfilled bodies with `todo!()` (it has type `!`, which coerces to any return type) if the file should compile while you fill them. The purple attribute dot above items generalises to outer attributes: `#[derive(...)]` (a multi-select of derivable traits, grayed when a field's type doesn't implement them), `#[cfg(...)]`, `#[test]`. The analog of Doodle's `@(test)` setup is to add `#[cfg(test)] mod tests { use super::*; }` when missing.
- **Ownership and borrowing.** Doodle's `Pass as` menu (`name`, `T(name)`, `&name`, `name^`) becomes `x`, `&x`, `&mut x`, `x.clone()`, `*x`, `x.into()`, `x.as_ref()`, `x.to_string()`. Gray with the reason rust-analyzer gives (value moved on line N; not declared `mut`) instead of hiding, and offer the fix as a Y option (make it `let mut`).
- **Lifetimes and generics.** Generic and lifetime parameters are dots in a `<...>` list, like Doodle's polymorphic `$T` params. Generated lifetime names need a taste decision (`'a`, `'b` is idiomatic; keep animals for value names). `where` clauses and bounds are a type-dot menu of traits in scope.
- **Pattern matching.** `match` arms work like Doodle's switch cases: a case dot offers the enum's variants, with variants already used grayed (advisory in Doodle; in Rust a repeated arm is only an `unreachable_patterns` warning, while a missing arm is error E0004, so an "add missing arms" option is essential; Odin is similar, an enum `switch` must list every value unless it is `#partial`). Patterns are nested dots (tuple, struct, `_`, bindings with generated names). Add `if let` / `let ... else` to the Branching group.
- **Option and Result.** The Error handling group becomes `?` (Odin's `or_return`; only valid when the enclosing fn returns a compatible `Result` / `Option`, so gray it otherwise), `.unwrap_or(●)` (Odin's `or_else`), `match`, `if let Some(x) = ● {`, `let Ok(x) = ● else { ● };` (let-else, stable since Rust 1.65; its `else` block must diverge: `return`, `break`, `continue` or a panic, so prefill it with `return ●`). Capture dots apply to calls returning `Result` too; note `#[must_use]` on `Result` makes an uncaptured call a warning, a good reason to keep the capture dot visible.
- **Closures.** A value-menu entry `Closure` -> `|●| ●` with parameter dots; `move` as a keyword toggled by Y.
- **Macros.** `println!` / `format!` / `vec!` / `assert!` behave like calls with typed dots; their format strings reuse word-by-word editing (Doodle already splits `{:v}`-style verbs; add `{}`, `{:?}`, `{name}`). Declarative macro *definitions* stay fixed text unless modelled.
- **Modules, visibility, use paths.** `use` is the Import menu (std, the crate's own modules, `Cargo.toml` deps); `pub` / `pub(crate)` / `pub(super)` is a keyword modifier toggled by Y and removed by LT+B, like Doodle's attributes. Other modules are read-only "siblings", but Rust's visibility is per module tree, not per file: from module M an item is visible if it is `pub`, `pub(crate)`, `pub(super)` / `pub(in path)` covering M, or private and declared in M or in an ancestor of M (a child module sees its parents' private items; a sibling module does not). The closest Odin analogs are `@(private="file")` (invisible elsewhere) and `@(private)` (package-wide); compute visibility with the oracle rather than with that analogy.
- **async.** `async` is a modifier keyword on fns; `.await` is a `Pass as` form on futures; gray `.await` outside async contexts (it is error E0728 there), and decide whether such grays are refused or advisory: Doodle refuses only in option menus.

**(d) Implementation advice.**
- Use a *lossless* syntax tree so invariant 9 holds by construction: rust-analyzer's syntax crate (`ra_ap_syntax`, a rowan CST) or `tree-sitter-rust`. Do not use `syn` for loading: it keeps only doc comments (as attributes) and drops ordinary comments, blank lines and all formatting, which breaks round-trip. tree-sitter keeps byte ranges into the original text rather than trivia tokens, so with it the "lossless" property comes from slicing the source by node ranges. Project the CST into Doodle-style lines of fields (fixed text, editable leaves, dots), so the "fields concatenate to the line" property can be tested directly.
- Use rust-analyzer as the type oracle (the `ra_ap_*` crates in-process, or the LSP). The key query is "expected type at this hole", plus what names are in scope. The LSP has no direct "expected type" request (completion and inlay hints use it internally), so an in-process `ra_ap_hir` / `ra_ap_ide` integration is the practical route; those crates publish a new, API-breaking version every week, so pin one. Keep Doodle's humility: when analysis is missing or slow, treat the type as `Unknown` and gray nothing. For determinism, compute menus synchronously from a fixed snapshot of the files, or record the oracle's answers in the trace like Doodle records speech text.
- Diagnostics: run `cargo check --message-format=json` (or flycheck) debounced about 0.6 s after edits on a worker thread, on a scratch copy of the crate with the document's current text as Doodle does (src/app/checker.odin) and its own `--target-dir` so it never blocks on the user's build lock; map spans to nodes, shade lines red, and keep the results out of the replay fingerprint (they only shade).
- Formatting: run `rustfmt` on load and save as Doodle runs `format_doc`, and lay out the view from rustfmt's line breaks so the view stays WYSIWYG. Pick one width (Doodle shows 80 columns; rustfmt's `max_width` defaults to 100) and use it in both places (`rustfmt.toml`). Caveat: rustfmt refuses a file that doesn't parse, and Doodle's saved holes (`x :=`, `case :`) are exactly that. Either substitute parseable placeholders before formatting and strip them after, or write a tolerant formatter over the CST as Doodle did (its `format_doc` is its own code, src/model/formatter.odin).
- Holes: decide early how unfilled holes are saved. Doodle saves them as nothing (the file doesn't compile until they're filled) and reloads them as dots. In Rust, `todo!()` in expression position would compile and round-trip, if every `todo!()` loads back as a dot (which also turns a deliberate, user-written `todo!()` into a dot; decide whether that is fine). Types have no general compiling placeholder: `_` works in a `let` annotation or a turbofish (`let x: _ = ...`, `collect::<Vec<_>>()`) but is an error in item signatures (E0121), so type holes in fn signatures, struct fields and consts stay non-compiling (or default to `()`). Write the rule down and test it as Doodle's reload tests do.
- Determinism: `std::collections::HashMap` iteration order is randomised per process. Never let it decide menu order, grouping, generated names or anything fingerprinted: use `BTreeMap` / `IndexMap` or sort. Seed or record every RNG (project names). Worker threads (speech, check, the oracle) send results over channels that are polled at a fixed point in the frame and recorded with their frame number.
- Persistence: plain line-oriented text with the `doodle-<kind> N` header (serde is fine for parsing, but keep the never-overwrite-newer, keep-unknown-lines and tmp-plus-rename rules). `std::fs::rename` replaces an existing target: atomically on POSIX within one filesystem; on Windows it uses `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`, the same call Doodle's heat save relies on (no atomicity guarantee there). Write the `.tmp` next to the target so both are on the same filesystem.
- Deck stack: SDL2 or SDL3 (`sdl2` crate with static linking, or `gilrs` + `winit`), OpenGL 3.3 via `glow` (or `wgpu`), text via `fontdue` / `ab_glyph`, Whisper via the same `whisper-cli` subprocess (isolation, reuse of the release artifacts) or `whisper-rs`. Build releases in the Steam Linux Runtime SDK as Doodle does.
- Testing: a `model` crate with no window or GPU dependencies and an `Input` struct like Doodle's; acceptance tests that build a real program from an empty project with controller-equivalent input, then run `cargo check` in a temp dir.

## Open questions & known gaps

1. **No undo history.** B restores only the step in progress; LT+B deletes are immediate and can't be undone (Grab keeps its own move log for B only). A Rust version should decide whether to add undo; it would not conflict with any principle.
2. **No unsaved-changes guard.** There is no dirty flag anywhere in src/app or the model. Opening another file (Files, Previous file), B from the editor to the main menu (which offers no way back to the document), then B there (quits at once), IDE menu > `Exit`, closing the window, and the self-updater's restart all drop unsaved edits silently. Only Run (Run list, Run favorite, Run tests) saves first (`save_current`). Deleting the open file in Files at least warns `This is the open file: the editor keeps its text, unsaved.` Whether this is deliberate is not stated anywhere.
3. **"Always compiles" is partial.** Unfilled required value/type holes save as non-compiling text (P4). This is deliberate for round-trip but contradicts EDITOR_MODEL.md §1.2.
4. **Name generator exhaustion.** With all 400 adjective_animal combinations of the requested casing used (in the document plus sibling procedures and types), `generate_ident` / `generate_type` / `generate_const` loop forever (`for { ... }` with no exit but a free name). EDITOR_MODEL.md's `_2` suffix rule is not implemented.
5. **Gray reasons are uneven.** Only the Key Layout picker gives a per-option reason; code menus give the type reason in a header line, and refused options (already present, wrong shape, label in use) and advisory context grays (`Break` outside a loop, a used case value) give none. The owner's intent ("gray out with a reason") suggests per-option reasons in the Rust version, e.g. a line under the grid for the highlighted gray cell, as Key Layout does under its title.
6. **Advisory grays are selectable, and not only type fits.** model.odin `menu_select` has no general dim check: every gray outside the three option-menu kinds still applies (a grayed leaf inserts, a grayed group opens). For type fits that is deliberate (heat.odin says so; the resolver is partial) and the acceptance test logs such picks as findings. For the context grays it lets the user insert code `odin check` rejects (`break` outside a loop, an import inside a `when`, a duplicate case value). Whether that is intended, and whether the UI should say "doesn't seem to fit, pick anyway?", is open.
7. **The HUD ignores overlay controls.** In Files, Run list, Save as, Docs, Settings, Recent Projects and New Project the HUD still shows the editor layout while the buttons mean something else (each overlay shows its own footer instead; confirmed by reading main.odin, where `draw_hud` runs unconditionally after the overlays and only Key Layout substitutes a bank). Files' own `LT+B delete` and `LT+X rename` happen to coincide with the default Delete / Talk buttons, which makes the mismatch easy to miss.
8. **Gray-versus-hide is not uniform.** The statement menu hides `Else`, `Default case` and `Fallthrough` where they don't apply, while Y's option menus gray `Add else` / `Add default case`. Pick one rule for the Rust version.
9. **First procedure is always `main` per file.** `append_proc_node` names the first procedure of *each document* `main` and ignores sibling files, so the first procedure added to a second file of a package redeclares the package's `main` (from code reading; no test covers it).
10. **B with a trigger on the main menu quits.** The `.Menu` branch of `update` reads `inp.cancel` instead of the keymap's leftover input, so LT+B or RT+B on the main menu quit like B, contradicting the "never falls through" rule (from code reading; test_menu_cancel_quits only checks plain B).
11. **Hidden footer.** The main menu's footer (including `(Open Folder not wired yet)`) is drawn at 84% of the window height, under the 150 px HUD at 1280x800, so it is invisible at the reference size (home.png confirms).
12. **Doc drift.** EDITOR_MODEL.md: radial menus, `_2` collisions, HUD scale and tween, "Save as always has a button", taxonomy rows not in code (Procedure group, Polymorphic procedure, Procedure type: only `Procedure` exists; see doc 04), the v1 main menu. docs/STT.md: always-listening mic, per-field grammars (the `.gbnf` files are unused by the app: src/stt/stt.odin supports `--grammar` but the app leaves `grammar_path` empty), synchronous transcription. README (Deck table, "Typing (file names, Files search)"): says Files search can be typed, but the code only takes dictation there (`Raw.typed` is read only by the Save-as / rename dialog). ARCHITECTURE.md's package map and MULTI_AGENT.md are historical.
13. **`run.txt` breaks the file convention.** It has no versioned header and is rewritten unconditionally.
14. **CRLF files** are converted to LF on save (`\r` stripped on load). This is a byte-level change despite the round-trip rule.
15. **Open Folder** on the main menu is not wired (shown dimmed).
16. **Linux deletes are permanent** (no trash; src/app/trash_other.odin deletes outright); only README warns about it. The in-app confirmation still says `It goes to the Recycle Bin (you can restore it from there).` and the status afterwards says `deleted x (in the Recycle Bin)` on every OS (src/app/filenav.odin), which is wrong on Linux.
17. **Screenshots are stale** (3-item main menu, LT+Y unbound, RT+X `>` for Run list, letter glyphs where the HUD now draws add / back / copy icons, no purple attribute dots); regenerate them for the Rust handoff with `tools/trace.py script ... --shot`.
18. **Taste questions for Rust** that Doodle never faced: generated lifetime names, whether `todo!()` is a dot, how to show borrow-checker refusals as grays with reasons, and what replaces Odin's tiny keyword set in the statement menu without bloating it (Rust has many more forms; the categories in P6 should stay at about 8 to 10 top-level groups).
