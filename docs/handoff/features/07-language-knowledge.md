## Purpose

A gamepad IDE cannot ask the user to type a name and hope it exists: every menu must already know
what is valid at the cursor. This area is where that knowledge comes from. It answers four questions
for the rest of the editor: (1) what packages can I import, and what procedures, types, constants,
struct fields and enum members does each one export (with signatures precise enough to create the
right number of typed argument dots); (2) what do the *other files of my package* declare, since in
Odin those names are usable without an import; (3) what is the documentation of the thing under the
cursor (LT+Y); and (4) does the code compile right now (a background `odin check` whose problems are
shaded on the affected lines). A fifth, smaller job runs before Run: noticing that an imported
vendor library needs a shared library (`SDL3.dll`) the system cannot find, and offering to fix it.
Everything here is local and offline; no language server is used.

## Features

### 1. Offline library tables generated from the toolchain install (developer-facing)

- **Trigger**: a developer runs, by hand, `python tools/gen_core_tree.py [ODIN_ROOT] [OUT_FILE]` and
  `python tools/gen_core_procs.py [ODIN_ROOT]`. `ODIN_ROOT` defaults to `$ODIN_ROOT`, else `C:\Odin`
  (tools/odin_collections.py `ODIN_ROOT`). Not run by the build or CI; the outputs are committed.
- **Behavior**: the scripts walk the three built-in *collections* of the Odin install
  (`core` = standard library, `base` = intrinsics/runtime/sanitizer, `vendor` = bundled third-party
  bindings such as sdl2, OpenGL, vulkan, raylib, directx) and emit Odin source files that are just
  big static array literals compiled into the binary (headers: `// AUTO-GENERATED by
  tools/gen_core_procs.py -- do not edit.` on the five `core_procs/types/consts/fields/enums`
  files, `// AUTO-GENERATED by tools/gen_core_tree.py -- do not edit by hand.` on core_tree.odin).
  Six generated files, eight tables (row counts at baseline; each script prints its counts):

  | File | Table | Rows | One row is |
  |---|---|---|---|
  | core_tree.odin | `CORE_ROWS` / `BASE_ROWS` / `VENDOR_ROWS` | 317 / 3 / 105 | a node of the Import menu tree |
  | core_tree.odin | `IMPORT_NAMES` | 11 | the alias a non-identifier package must be imported as |
  | core_procs.odin | `CORE_PROCS` | 74,682 (297 packages) | a public procedure with its signature |
  | core_types.odin | `CORE_TYPES` | 14,257 (269 packages) | a type declaration |
  | core_consts.odin | `CORE_CONSTS` | 22,563 | a constant and its "kind" |
  | core_fields.odin | `CORE_FIELDS` | 29,341 (5,641 structs) | one field of one struct |
  | core_enums.odin | `CORE_ENUM_MEMBERS` | 48,084 (2,657 enums) | one member of one enum |

  Row shapes are in "Data model & formats" below. The import path of every row is the Odin import
  string, `"<collection>:<relative folder>"`, e.g. `core:sys/windows`, `vendor:sdl2/image`.

  *Which folders are packages* (tools/odin_collections.py, gen_core_tree.py `scan`): a folder is an
  importable package when it has at least one non-`_test.odin` file, is not the collection root,
  is not `base:builtin` (`NOT_IMPORTABLE`: it only documents predeclared names), is not a program
  (`package main`, detected from the first non-test file with comments stripped, because doc files
  often show `package main` in examples), and (tree only) has no column-0 file-scope `#panic(` in a
  file that builds on Windows (vendor:libc "has been moved", deprecated core:path refuse import).
  Directories named `tests`, `examples`, `example`, `_gen` and dot-directories are never entered.

  *What counts as a declaration* (gen_core_procs.py `scan_file`, `scope_lines`): comments are blanked
  first (nested `/* */` handled, line/column positions preserved), then each line is classified as
  file scope (possibly inside top-level `when` blocks, which is how OpenGL and sdl2 declare
  everything), directly inside a file-scope `foreign <lib> {` block, or anything else (ignored).
  Recognized at file scope: `name :: proc(...)`, `name :: proc "c" (...)`, `name :: #force_inline
  proc(...)`, proc groups `name :: proc{a, b}`, bodiless declarations ending in `---`
  (base:intrinsics), procedures inside foreign blocks (the block's library name is kept as the row's
  `block`), intrinsic aliases `L :: intrinsics.constant_utf16_cstring` (signature known only for
  entries in `INTRINSIC_SIGS`: `L(value: string) -> cstring16`), globals whose type is a `#type
  proc` of the same package (`CreateInstance: ProcCreateInstance` in vendor:vulkan becomes callable
  with that proc type's signature), type declarations, typed and untyped constants.

  *Exclusions*: `_test.odin` files, `example.odin` (demo code inside some packages), files whose
  header has any `#+private` tag (nothing in them is visible to importers), declarations with an
  attribute containing `private` (on the same line or attribute lines above, including a
  `@(private) foreign lib {` block, which hides all its members), names starting with `_`, and
  `main`. Vendor packages that cannot build on Windows (darwin/*, android/*, x11, egl, wasm) are
  left out of the proc/type/const/field/enum tables (they still appear, platform-tagged, in the
  Import tree). Core packages are not filtered this way (core:sys/linux and core:sys/darwin/* are
  in the tables).

  *Platform preference* (`windows_score_for_file`, `when_cond_score`, `combine_scores`): each
  declaration gets a Windows score: 2 = Windows-only, 1 = any OS, 0 = some other OS. It comes from
  the file name suffix (`foo_windows.odin` = 2; `_linux`, `_darwin`, `_js`, `_posix`, ... = 0), the
  file's `#+build` lines (`!windows` = 0; a positive `windows` token = 2; only other OS tokens = 0),
  and enclosing `when` conditions (`ODIN_OS == .Windows` = 2; `ODIN_OS != .Windows`, or `ODIN_OS ==`
  any other OS such as `.Linux`, = 0; any other condition = 1; an `else` after a Windows branch = 0,
  an `else` after a `!= .Windows` branch = 2; nested conditions combine: any 0 gives 0, else any 2
  gives 2). The file-name rule looks at every `_`-separated part after the first
  (`thread_linux_amd64.odin` = 0). When one file declares a name several times (per-OS `when`
  branches), the highest score wins, the first one on a tie (key: name + kind + foreign library).
  Struct and enum bodies are chosen the same way across all files of the package (files are read in
  sorted order). Rows for the same name in *different files* are all kept (see Open questions:
  `core:fmt` keeps both `fmt_js` and `fmt_os` rows of `println`), but every row of one name carries
  the same *package-wide* merged signature (`resolve_sigs` is keyed by name per package), so at
  baseline rows of one `(path, name)` never disagree.

  *Signatures* (`signature_after`, `param_arity`, `return_text`, `resolve_sigs`): the text inside
  the parameter parens is taken bracket-balanced across up to `MAX_SIG_LINES = 60` lines and
  whitespace-normalized into `params`. `req` counts required parameters: grouped names each count
  (`a, b: int` = 2), a default makes a parameter optional (`x := 1`, `x: T = 1`), `..T` or
  `#c_vararg` makes the procedure `variadic`. The return text after `->` (up to `{`, `---` or
  ` where `) becomes `ret`: `-> !` (diverging) becomes `""`, a single named result `(n: int)` becomes
  `int`, multiple results stay as written (`"(T, bool) #optional_ok"`). Merging rules: a proc group
  takes the minimum `req` of its members, is variadic if any member is or their arities differ, and
  has `params = ""`, `ret = "?"`; the same name with different signatures in one package keeps
  params with `ret = "?"` if only the return spelling differs, else becomes
  `(min req, variadic, "", "?")`; an unparseable signature is `(0, variadic, "", "?")`. Aliases
  `A :: SomeProc` in the same package get the target's signature (fixed point); cross-package
  aliases `CreateWindow :: glfw.CreateWindow` are resolved after every package is scanned
  (`resolve_cross_aliases`) into a proc, type or constant of the aliasing package; unknown targets
  fall back to a guess (CamelCase = type, otherwise constant of kind `"?"`).

  *Types* (`classify_decl`, `resolve_types`): `struct`, `enum`, `union`, `bit_set`, `bit_field`,
  `distinct X` and aliases. A polymorphic struct/union keeps its parameter list as `target`
  (`"($T: typeid)"`) so consumers know it cannot be used bare; a bit_set keeps its whole spelling
  (`"bit_set[Flag; u8]"`) so the element enum can be found; `#type proc ...` and `[N]T`, `^T`,
  `map[K]V`, `matrix[...]` are aliases, but `[4]f32{1, 2, 3, 4}` (has `{`) is a constant. A bare
  identifier alias `A :: B` is a type only if `B` is (resolved to a fixed point within the package),
  so `LPCWSTR :: wstring` is a type while `MB_ICONINFORMATION :: MB_ICONASTERISK` is a constant.

  *Constant kinds* (`const_kinds`): untyped literal kinds `#int` / `#float` / `#string` / `#rune` /
  `#bool`; a type name for typed constants (`X : DWORD : 1`, `X :: DWORD(1)`, `X :: Foo{...}`);
  expressions of other constants resolved to a fixed point (a named type among the parts wins; only
  ints/floats/runes gives `#float` if any float else `#int`; mixed gives `"?"`); `1 << 3` or
  `size_of(u32) * 2` with no names gives `#int`; an expression containing a cast to a known type
  (`~DWORD(0)`) takes that type first; an expression containing a string or rune quote that is not
  itself a literal is left `"?"`; anything else `"?"`. Right-hand sides starting with
  `#config`, `#load`, `#directory`, `#file`, `#line`, `#location`, `#procedure`, `#force_inline`,
  `#force_no_inline`, `proc`, `#type`, `struct`, `enum`, `union`, `nil` or `---` are not constants
  (`NOT_CONSTANTS`); a typed declaration `X : T : v` whose `T` starts with `proc` or `#` is not one
  either. Proc aliases (`emit_x :: emit_x_r_r_r`) are removed from the constants. Baseline
  distribution: 13,759 `#int`, 2,079 `#string`, 251 `#float`, 63 `#rune`, 42 `#bool`, 5,348 typed,
  1,021 `"?"`.

  *Struct fields* (`parse_struct_fields`): one row per field in declaration order; `a, b: T`
  expands to two rows; padding fields named `_` are dropped; struct tags (`"json:x"`) and
  `#subtype` are stripped; an anonymous nested struct/union type is written `"?"`;
  `using _: struct #raw_union {...}` (OVERLAPPED) and `using _: bit_field DWORD {...}` (DCB) are
  *flattened*: their promoted fields are listed as plain rows in place, because Odin accepts both
  `x.Offset` and `T{Offset = 1}`; `using name: NamedType` stays as one row with `using_field =
  true` and the consumer expands it (var_types.odin `append_promoted`).

  *Enum members* (`parse_enum_members`): names only, in order; values and comments dropped.

  *Import tree* (gen_core_tree.py): per collection, (a) prune folders with no importable package
  beneath; (b) `collapse` a non-importable group with exactly one child into a path label
  (`compress/lz4`, `intrusive/list`); (c) `sink_internals`: when two or more importable children of
  a group are imported only by packages inside that group's subtree, move them into a dimmed
  `internals` subgroup (decluttering); (d) `group_platform`: a group whose children share one
  platform tag takes that tag (so vendor:darwin hides as a whole); (e) `emit` depth-indented rows:
  children sorted with dim last then by lower-case name; an importable folder that also has children
  becomes a group row followed by a first child leaf labelled `"import <name>"`. Folders whose name
  is not an identifier (`vendor:lua/5.4`, `vendor:libc-shim`, `core:odin/doc-format`) get an
  `IMPORT_NAMES` row (`import_name`: a version folder takes its parent's name, `lua/5.4 -> lua`;
  other characters become `_`, `libc-shim -> libc_shim`).

  *Platform tags* (`package_platform`): authoritative path prefixes first (`PATH_PLATFORMS`:
  core:sys/windows = `windows`, core:sys/linux = `linux`, core:sys/darwin = `darwin`, vendor:darwin
  = `darwin`, vendor:android = `android`, vendor:windows and vendor:directx = `windows`, vendor:wasm
  = `js`, vendor:x11 = `linux,freebsd,openbsd,netbsd`, ...); otherwise, if every non-test file has
  a `#+build` line, the union of positive OS tokens; otherwise fallbacks (core:sys/posix and
  core:sys/unix = `linux,darwin,freebsd,openbsd,netbsd`, core:sys/kqueue, core:sys/valgrind);
  otherwise `""` = builds everywhere.
- **Rules & edge cases**: the tables are never modified at runtime; their strings are static and
  must never be freed by consumers (comments in model.odin `procs_for_path`). Lookups that would
  scan 14k-29k rows per query use lazily built maps (`core_type_index`: `"path|name"` -> first row;
  `core_field_range`: `"path|type_name"` -> `[lo, hi)` row range), built once with `sync.Once` on
  the heap allocator and kept for the whole run (typecheck.odin, var_types.odin).
- **Rationale**: stated in the script docstrings: Doodle runs on Windows first (Windows variants
  win; vendor packages that can't build there "would only add dead weight"); bucketing and
  usage-first ordering are left to runtime "since they depend on counts/user state".
- **Source**: tools/gen_core_procs.py (`scan_file`, `scope_lines`, `classify_decl`, `const_kinds`,
  `resolve_sigs`, `collect_package`, `resolve_cross_aliases`, `parse_struct_fields`),
  tools/gen_core_tree.py (`scan`, `collapse`, `sink_internals`, `group_platform`, `emit`),
  tools/odin_collections.py (`package_platform`, `windows_score_for_file`, `import_name`,
  `has_file_scope_panic`, `is_program`).

### 2. Import menu: the four collections

- **Trigger**: on a file-scope insertion point (green dot) press A (menu title `Add  (insertion
  point)`), then `Dependencies` > `Import` or `Aliased import` (the menu tree itself belongs to 04;
  `Dependencies` holds `Import`, `Aliased import`, `Foreign import`, `Foreign block` in that order).
  Also LT+A (`Edit`) on *any* part of an `import` line (model.odin `edit_selected`, case 2: the
  node's text starts with `import `) opens the whole Add menu again, titled `Edit import`, with
  `Dependencies` highlighted (not opened); picking an import leaf under it *replaces* that line in
  place (`app.replacing`, `replace_fi = -1`) instead of inserting a new one.
- **Behavior**: both entries open the same four groups in this order: `core`, `base`, `vendor`,
  `shared` (collections.odin `build_import_collections`). core/base/vendor are built from the
  generated rows (`build_rows_tree` turns depth-indented rows into nested menu entries). `shared` is
  listed from disk: every sub-folder of `<odin_root>/shared` (up to 4 folder levels below
  `shared/`, skipping dot, `tests` and `examples` folders) holding a non-test `.odin` file becomes a
  leaf labelled by its
  relative path (`gfx/sprites`) inserting `import "shared:gfx/sprites"`, sorted. With no packages
  the group holds one dimmed, non-actionable row `(empty: add packages to <root>/shared)`.
  Picking a leaf inserts `import "core:fmt"`; under `Aliased import` it inserts
  `import fmt "core:fmt"` with the alias editable (default = last path segment, `alias_default`).
  The path itself is a non-editable cursor stop (field kind `import_path`, model.odin
  `import_node`). An importable group shows `import <name>` as its first entry, then its
  sub-packages, e.g. `core > c > import c | libc`. A non-importable group whose only content is
  versions shows just those (`vendor > lua > 5.1 | 5.2 | 5.3 | 5.4 | 5.5`, no `import lua`).
  In replace mode (`Edit import`), a leaf picked under plain `Import` drops any alias the old line
  had (unless the new path needs one, feature 4); under `Aliased import` it gets the default alias.
- **Rules & edge cases**:
  - `odin_root()` (collections.odin): `$ODIN_ROOT` (trimmed, trailing slashes removed), else the
    folder of `odin.exe`/`odin` found on `PATH`, else `C:/Odin`. (Not the same search as the
    compiler finder; see Open questions 1.)
  - The whole Add-menu tree, including the `shared` listing, is built lazily once per App by
    `ensure_menus` (it returns at once when `app.add_menu != nil`) and reused; packages added to
    `shared/` during a session are not seen until restart. Verified: `free_menus` (the only thing
    that resets `add_menu`) is called only on the throwaway scratch App in siblings.odin and in
    tests, never on the editor's App. docs/EDITOR_MODEL.md says "listed when the menu opens" and
    the collections.odin header "listed when the menu is built"; only the latter is accurate: the
    code builds it at the first open of any menu that calls `ensure_menus` (Add, IDE menu, LT+A on
    an import or a type field).
  - The `shared` listing applies only some of the generator's filters: a folder whose only `.odin`
    files are `_test.odin` is skipped (the check is "has a non-test `.odin` file"), but a
    `package main` folder or one with a file-scope `#panic` is listed. A folder that holds `.odin`
    files *and* sub-packages is listed itself and its sub-folders are listed too, all as flat
    sibling leaves sorted by path (`gfx`, `gfx/sprites`); there is no nesting under `shared`.
  - `base:builtin` never appears (test `test_import_base_lists_importable_packages`).
  - Dimmed `internals` groups are only drawn dim; they remain enterable and their leaves insertable
    (`menu_select` has no dim guard). The generator sorts them last, but `make_view` re-sorts any
    view with more than 12 entries case-insensitively by label, so in a big group `internals` lands
    alphabetically under "i".
  - Inside a file-scope `when` block (the insertion point is indented, ctrl.odin
    `ctrl_add_menu_opened`), the `Dependencies` group is drawn dimmed, as a hint that imports don't
    belong there; it is still enterable.
  - Ordering inside any view (model.odin `make_view`): already-imported leaves first (a leaf counts
    as imported only when some line's text is exactly `import "<path>"`, so an *aliased* import of
    it does not), then recently used import paths (most recent first, `record_recent`), then pinned
    entries; this forms a separate "recent" section when more follows; the rest keeps its order,
    except that a remainder longer than `BUCKET_THRESHOLD = 12` is sorted case-insensitively and
    shown as a flat scrollable grid (no buckets at this level).
  - Each pick of an import path (insert or replace) is moved to the front of `recent_imports`
    (session memory, no cap, not persisted by this code).
- **Source**: collections.odin (`build_import_collections`, `odin_root`, `build_shared_tree`,
  `list_shared_packages`), model.odin (`build_rows_tree`, `make_view`, `ensure_menus`,
  `record_recent`, `import_node`, `alias_default`).

### 3. Packages for another OS are hidden

- **Trigger**: any menu view built from platform-tagged entries (the Import tree).
- **Behavior**: `make_view` drops every entry whose `platform` is non-empty and does not contain
  `app.os_name` as one of its comma-separated tokens (`platform_ok`). `app.os_name` is set at
  startup from the build target: `"windows"`, `"linux"` or `"darwin"` (src/app/main.odin
  `os_name`). On Windows the vendor list shows `directx`, `OpenGL`, `raylib` but not `darwin` or
  `android`; on Linux (Steam Deck) `core:sys/windows` and `vendor:directx` disappear while
  `core:sys/posix` (`linux,darwin,...`) stays.
- **Rules & edge cases**: an empty tag matches every OS. Filtering happens per view, so a hidden
  group hides its whole subtree.
- **Source**: model.odin `platform_ok`, `make_view`; tests `test_vendor_platform_groups_filtered`,
  `test_make_view_filters_platforms`, `test_platform_ok_*`.

### 4. Non-identifier package names are always imported with a name

- **Trigger**: picking a package whose last folder is not an identifier (`vendor:lua/5.4`,
  `vendor:libc-shim`, a runtime-listed `shared:my-lib`).
- **Behavior**: even from plain `Import`, the inserted line is aliased because
  `import "vendor:lua/5.4"` would not compile: `import lua "vendor:lua/5.4"`. The name comes from
  `IMPORT_NAMES` (`import_name_for`) or, for shared packages, the same rule computed at runtime
  (`alias_default`: version folder -> parent name; other chars -> `_`; a leading digit gets `_`).
- **Rules & edge cases**: `needs_import_alias(path)` is true when the text after the last `:` or `/`
  is not an identifier. `collect_imports` then reports the reference as `lua`. A blank import
  (`import _ "..."`) is skipped by `collect_imports` (nothing to call through).
- **Source**: collections.odin (`import_name_for`, `needs_import_alias`), model.odin
  (`alias_default`, `collect_imports`, menu confirm branch for `e.import_path`); test
  `test_import_lua_gets_a_name`.

### 5. Calls > From import: a package's procedures, with signature-driven argument dots

- **Trigger**: on a statement dot (green body dot) press A > `Calls` > `From import`; on a value dot
  (or a variadic `args` dot) A > `Call` > `From import`; on an `if`/`switch` setup dot A > `Call`
  (branch.odin `branch_slot_menu`). All three build the same children with `build_call_children`
  (the statement menu's `Calls` entry carries heat key `"Call"`, so heat is shared, 03/06). Its
  three groups are always, in this order: `Internal procedure`, `From import`, `Built-in`
  (features 7 and 9 cover the other two). Y (`Change`) on a call's name reuses the same package
  list (`build_import_proc_menu`) in a menu titled `Change procedure` (change.odin
  `open_change_call_menu`; owned by the editing docs).
- **Behavior**: one group per import of the open document, in document order, labelled with its
  reference (alias or last path segment: `fmt`, `win`; `collect_imports`, duplicates of the same
  ref+path once), whose heat key is the import path (heat shared across aliases, 03). Inside:
  procedures of that path from `CORE_PROCS`. Names already called in this file as `ref.name(` are
  pinned at the top; the rest are grouped (feature 6). Picking a procedure replaces the dot with
  three fixed (non-editable) fields `ref`, `.`, `name` followed by argument dots built from its
  signature (calls.odin `inject_call_args`); if the dot was a statement (`body`) dot, a new line
  holding a fresh statement dot is inserted below (model.odin `make_import_proc_call`):
  - no parameters and not variadic: `(` `)` as two separate fields (so the name stays selectable);
  - `req` required parameters: one orange value dot per required parameter, comma-separated, each
    carrying the parameter's declared type as its *hint* (`hint_pkg` = the package path, so
    `LPCWSTR` is resolved inside core:sys/windows);
  - variadic: a trailing green `args` dot that repeats (filling it appends `, ●` of the same type).

  Example (core:sys/windows, `win.MessageBoxW` is `req 4`, params `hWnd: HWND, lpText: LPCWSTR,
  lpCaption: LPCWSTR, uType: UINT`, ret `INT`):
  ```odin
  // before (statement dot)
  	●
  // after
  	win.MessageBoxW(●HWND, ●LPCWSTR, ●LPCWSTR, ●UINT)
  ```
  (A dot is drawn as ● followed by its hint label in the UI font: the expected type for a value
  dot, `..T` for an args dot, nothing when the hint is empty; src/app/main.odin `slot_hint_label`,
  used by the editor layout in src/app/editor_view.odin and by the fill menu's header line
  `expects <label>  -  grayed options don't fit`.) `fmt.println` (`req 0`, variadic, params
  `args: ..any, sep := " ", flush := true`) becomes `fmt.println(●..any)` with a single repeating
  green args dot. The return type (`ret`, `ret_pkg`) then drives the capture dot and type fitting
  (05/06).
- **Rules & edge cases**:
  - Signature lookup (`call_signature`): the import reference is mapped to its path through the
    document's imports, then every `CORE_PROCS` row with that path and name is read; if several rows
    disagree on `req`/`variadic` (per-OS files), the result is permissive: min `req`, variadic,
    no params, `ret = "?"`. If they agree on `req`/`variadic` but differ otherwise, the first row
    wins. (At baseline the generator already merged them per package, feature 1, so this runtime
    merge is a safety net.)
  - An unknown procedure (not in any table) gets `req 0` + variadic: `name(●args…)` so the user can
    still add any number of arguments. Unknown is never an error. A `ref` that names no import of
    the document gives the same unknown shape.
  - A package with no table rows (a `shared:` or relative import, or a vendor package left out of
    the tables such as vendor:x11 on Linux) shows a single entry `Other (name it yourself)` (fill
    `__call_import__`), which inserts `ref` `.` `<generated name>` with only the name editable,
    then `(●)` with one untyped repeating args dot (model.odin `make_call_import`, 08). In the
    fill menus this entry is never grayed out (typecheck.odin `entry_fits`: "can't tell").
  - No imports at all: a dimmed, non-actionable `(no imports yet)` row. No procedures in this file
    or its siblings: `Internal procedure` holds a dimmed `(no procedures defined)` row.
  - Used-name detection (`collect_called_procs`) is textual: for each line it finds only the
    *first* occurrence of `ref.` (a plain substring, so `myfmt.` also matches `fmt.`) and takes
    everything up to the next `(` as the name. A line like `foo(win.MB_OK, bar())` therefore pins a
    bogus entry labelled `MB_OK, bar` under `win` (inferred from the code; no test covers it). The
    Constant and Type menus use a stricter scanner (`collect_used_names`: whole identifiers only,
    every occurrence, and only names that exist in the package).
  - `ret` text conventions: `""` = returns nothing (`RET_NONE`), `"?"` = unknown (`RET_UNKNOWN`).
- **Source**: model.odin (`build_call_children`, `build_import_proc_menu`, `collect_called_procs`,
  `procs_info_for_path`, `make_import_proc_call`, `make_call_import`), calls.odin

### 6. Taming huge packages: file, foreign-block, prefix and alphabetical grouping

- **Trigger**: opening any package group built from table rows: Calls/From import, Constant
  (`build_import_const_menu`), Type (`build_import_type_menu`) and Struct literal
  (`struct_types_for_path`) groups reuse the same builder by casting their rows into the procedure
  row shape (`consts_info_for_path`: `block = ""`, `ret` = the constant's kind;
  `types_info_for_path` / `struct_types_for_path`: the `block` slot holds the type kind), then
  `retarget_leaves` turns the leaves' fill into `__const_import__`, `__type_import__` or the struct
  literal fill. Consequence: in a big package the Type menu's second level is the *kind*
  (`alias`, `distinct`, `enum`, `struct`, ...) inside each file group, since every type row has a
  non-empty "block"; constants never get a block level. Struct literal groups list only rows of
  kind `struct` with an empty `target` (no polymorphic structs) and do *not* pin used names (they
  pin the dot's expected struct type instead, 06).
- **Behavior** (model.odin `build_proc_hierarchy` and helpers; constants at model.odin top):
  1. Used names first (pinned, `pinned = true`).
  2. `FLAT_MAX = 60`: a list of 60 or fewer is shown flat, sorted by name (byte order, so
     upper-case names first; `make_view` re-sorts case-insensitively when the view has more than 12
     non-pinned entries).
  3. More than 60: group by source *file stem* if there is more than one file (`kernel32`,
     `user32`, `gdi32`, `util`... for core:sys/windows, 1,338 procedures). File groups are sorted.
     A file with 60 or fewer names is a flat list inside its group.
  4. Inside one file, more than 60: group by *foreign block* if there is more than one non-empty
     block; procedures outside any block go into a `(top-level)` group (e.g. core:sys/windows
     `kernel32` file: blocks `kernel32` (309), `one_core` (5) and `(top-level)` (3)). One non-empty
     block (or none): this level is skipped.
  5. Inside one block, more than 60: split by *name prefix*. `extract_prefix`: for a name containing
     `_`, everything up to and including the first underscore (`MB_`, `WM_`, `window_`); otherwise
     the PascalCase first word (up to the next capital: `GetWindowTextW -> Get`, `glClear -> gl`);
     a name with neither (`alloc`) has no prefix. Prefixes shared
     by at least `MIN_PREFIX_SHARE = 3` names become groups labelled `<prefix>...` (`Get...`,
     `MB_...`). A prefix group over 60 is split into alphabetical buckets. Names whose prefix is
     not shared stay reachable: listed flat beside the groups if there are 60 or fewer of them, else
     put into an `other...` group of alphabetical buckets. Everything is sorted by label.
  6. No qualifying prefix: alphabetical buckets of `PAGE = 12` names, labelled by the lower-case
     first letters of their first and last names (`a-c`, or `w` when both start with w). Each
     bucket's heat key is `"<first>..<last>"` so identically labelled buckets (all `w` inside
     `WM_...`) stay distinct for the heatmap (03).
- **Rules & edge cases**:
  - The grouping is always built from the package's *full* name list, then the names used in this
    file are removed from it (`remove_named_leaves`, which also drops groups left empty) and shown
    pinned on top. So group labels and shapes are the same in every project; only the pinned list
    differs (stated rationale: menu trails and their heat must not depend on what a file already
    uses).
  - `make_view` additionally sorts any view with more than 12 non-pinned entries case-insensitively.
  - `BUCKET_TARGET = 9` is declared but unused.
- **Rationale**: commit 8422cf0 ("Improve import procedure drill-down: capture foreign blocks,
  hierarchical grouping"; its test checks "fmt menu has groups, not flat 100+ items") and the
  `remove_named_leaves` comment (trails and heat must not depend on the file). A d-pad cannot
  usefully scroll a flat list of 1,338 Win32 procedures. (The "a few presses reach any name" goal
  is an inference from the shape, not a stated or tested bound.)
- **Source**: model.odin (`build_proc_hierarchy`, `build_file_children`, `build_block_children`,
  `build_flat_leaves`, `build_alpha_buckets`, `group_by_file`, `group_by_block`,
  `find_prefix_groups`, `extract_prefix`, `remove_named_leaves`, `make_view`), consts_menu.odin
  (`consts_info_for_path`, `build_import_const_menu`), types_menu.odin (`types_info_for_path`,
  `collect_used_names`, `retarget_leaves`, `build_import_type_menu`), struct_lit.odin
  (`struct_types_for_path`); tests `test_heat_alpha_buckets_have_distinct_keys`,
  `test_heat_grouping_ignores_used_names`, `test_no_bucketing_for_small_menu`,
  `test_bucketing_for_large_menu`, `test_procs_info_captures_foreign_procs`,
  `test_import_menu_hierarchical`.

### 7. Calls > Built-in: the hand-written table of compiler built-ins

- **Trigger**: `Calls` (or `Call`) > `Built-in`.
- **Behavior**: built from `BUILTIN_PROCS`, whose table order is: `len, cap, size_of,
  align_of, offset_of, offset_of_by_string, type_of, type_info_of, typeid_of, card, make, new,
  new_clone, delete, free, free_all, append, non_zero_append, inject_at, assign_at, pop, pop_safe,
  pop_front, pop_front_safe, ordered_remove, unordered_remove, remove_range, clear, resize, reserve,
  shrink, copy, delete_key, map_insert, map_upsert, map_entry, raw_data, min, max, abs, clamp,
  complex, real, imag, jmag, kmag, conj, swizzle, expand_values, compress_values, soa_zip,
  soa_unzip, container_of, assert, ensure, panic, unimplemented, unreachable` (58 entries, grouped
  in the source as lengths/sizes, allocation, arrays/maps, math, structs/#soa, control). The menu
  does *not* show this order: the group view goes through `make_view`, and with 58 (> 12)
  non-pinned entries it is shown sorted case-insensitively (`abs, align_of, append, assert, ...`).
  Each row is `{name, req, variadic, ret}`; e.g. `copy` = 2 required, returns `int`; `append` = 2
  required + variadic; `inject_at` = 3 + variadic; `swizzle` = 3 + variadic; `free_all` = 0;
  `unreachable` = 0, returns nothing. Picking one inserts the fixed name then `(` + dots + `)`
  exactly like a procedure of this file (`__call_this_pkg__`, model.odin `make_call_this_package`).
- **Rules & edge cases**: `call_signature` checks built-ins before this file's procedures (a
  same-named procedure in the file is shadowed by the built-in). Built-ins have no parameter types
  (`params` empty) so their dots carry no hints; `ret = "?"` where the result depends on the
  arguments (`make`, `new`, `min`). `quaternion` is left out (its arguments must be named; positional
  dots can't express that), as are the per-type members of groups (`append_elem`, `make_slice`).
  The list was checked by hand against `base/builtin/builtin.odin` and the `@builtin` procedures of
  `base:runtime` (comment).
- **Source**: builtin_procs.odin (`BUILTIN_PROCS`, `builtin_proc`), model.odin
  `build_call_children`; test `test_builtin_procs_signatures`.

### 8. The tables behind type-driven menus (overview; menus themselves are in 06)

- **Trigger**: value/type dots and member access (06).
- **Behavior**: `CORE_TYPES` feeds the `Type` fill menu's per-import groups (`win.` -> HWND,
  LPCWSTR, RECT...), the `Struct literal` list (only rows with kind `struct` and empty `target`, so
  polymorphic structs are excluded), and type resolution: `resolve_type` follows alias/distinct
  rows down to a builtin (`LPCWSTR -> wstring -> cstring16`) to decide which literals and calls fit a
  slot. Struct literal order: the dot's expected struct type pinned first (written with this file's
  alias, `win32.WNDCLASSW`), then one `ref.` group per import with struct rows, then this file's
  non-polymorphic structs, then the siblings' (not shadowed); a dimmed `(no struct types)` when
  empty (struct_lit.odin `build_struct_lit_entries`). `CORE_CONSTS` feeds the `Constant` menu (one group per import labelled `win.`, entries
  inserting `win.MB_OK`; `(no imported constants)` when none) and `const_fits` (an untyped `#int`
  fits integer and float slots; a typed constant must resolve to the same type; `"?"` fits
  anything). `CORE_FIELDS` feeds `Field of p`, struct-literal field dots and typed hints
  (`x   f32`). `CORE_ENUM_MEMBERS` feeds `Enum value` (`.North`) and switch cases.
- **Rules & edge cases**: anything that cannot be resolved is category `Unknown` and is *never*
  grayed out (typecheck.odin header). A reference `ref.Name` inside a type text is resolved
  best-effort (var_types.odin `ref_path`): written in the open document, `ref` must be one
  of its import references; written *inside* a table package (a `CORE_FIELDS` row's type such as
  `c.int`), the document's imports are not consulted: `ref` resolves to the first `CORE_TYPES` path
  equal to `core:<ref>` or `base:<ref>`, else to any path ending in `/<ref>` (core and base first so
  `.../runtime` can't shadow base:runtime); `builtin.X` means the builtin `X`.
- **Source**: types_menu.odin, consts_menu.odin, struct_lit.odin, typecheck.odin
  (`resolve_type`, `core_type_index`), var_types.odin (`collect_fields`, `core_field_range`),
  ctrl.odin (enum members); tests `test_windows_constant_kinds`, `test_resolve_windows_types`,

### 9. Sibling files: procedures of the other files in the package

- **Trigger**: automatic. An Odin package is a whole folder, so names declared at file scope in the
  other `.odin` files of the open file's folder are usable without an import. `refresh_siblings`
  (src/app/save.odin) calls `model.load_siblings(dir, own_file)` when the open file changes, on
  every save (`set_current_file` defers it "even for the same path"), and when the project folder
  changes while the document is unsaved. For an unsaved document the folder is the project folder
  and the document is assumed to be `main.odin` (a `main.odin` on disk there is excluded). Never on
  the per-frame path.
- **Behavior**: every top-level line of the form `name :: proc...` (column 0, exact spacing
  `" :: proc"`) in another file is kept as `{name, sig, file}` where `sig` is the declaration line,
  joined with following lines (trimmed, space-separated) until its parentheses balance:
  `long_one :: proc( a: int, b: bool, ) -> (int, bool) {`. These names appear under `Calls` >
  `Internal procedure` after this file's own procedures (deduplicated; `collect_proc_names`, which
  finds this file's own procedures by the text ` :: proc(` and takes the line's first editable
  field as the name), and `call_signature`
  parses `sig` exactly like a procedure of this file, so sibling calls get typed dots, a capture dot
  when they return something, and fill-menu graying.
  ```odin
  // new_file.odin (sibling, read-only)
  shout :: proc(s: string, times: int) -> string { return s }
  // main.odin (open): statement dot > Calls > Internal procedure > shout
  	shout(●string, ●int)
  ```
- **Rules & edge cases**:
  - Visibility: `@(private="file")` (any spacing, on the same line or on attribute lines just
    above, comments between allowed) hides a procedure; a file whose header has `#+private file`
    contributes nothing. `@(private)` and `#+private` (package-private) remain visible, because the
    open file is in the same package.
  - Indented lines are ignored, so procedures inside a file-scope `when` block of a sibling are not
    seen (types are; see feature 10). `// comment` lines and blank lines between an attribute line
    and its declaration are skipped without forgetting the attribute; any other non-matching
    top-level line forgets it.
  - The match is the literal substring ` :: proc`, so `name :: #force_inline proc(...)` /
    `#force_no_inline` procedures in a sibling are *not* seen (inferred from the code), while
    `name :: proc "c" (...)` is.
  - A proc group `name :: proc{a, b}` is listed but its signature cannot be parsed, so calls to it
    get the unknown-procedure shape.
  - Duplicate names across siblings are all kept in `sibling_procs`; the menu deduplicates and
    `sibling_sig_line` uses the first (directory order).
  - Lookup order in `call_signature`: built-ins, then this document, then siblings (first match).
  - Generated names (`generate_ident`) never collide with sibling procedure or type names
    (namegen.odin `is_name_used`).
- **Source**: siblings.odin (`load_siblings`, `scan_sibling_procs`, `attr_file_private`,
  `file_is_private`, `sibling_sig_line`), model.odin `collect_proc_names`, calls.odin
  `call_signature`, src/app/save.odin (`refresh_siblings`, `set_current_file`,
  `set_project_dir`); tests in siblings_test.odin.

### 10. Sibling files: types of the other files in the package

- **Trigger**: same loading as feature 9.
- **Behavior**: each sibling file is parsed with the editor's *own* parser into a throwaway App
  (`doc_from_source` into a scratch `App`), so its types are recognized by exactly the rules used
  for the open file. For every file-scope declaration that is a type (struct, enum, union,
  bit_field, bit_set, distinct, alias), a `#type proc` (kind `proc_type`), or a bare-name
  declaration `Vec :: point` (kind `ident`, decided later), the declaration text after `::` through
  the end of its brace block is kept, lines joined with `"\n"` as saved:
  `point :: struct { x: f32, y: f32, z: f32, point_or_vector: i8, }` is stored as
  `{name "point", kind "struct", text "struct { x: f32, y: f32, z: f32, point_or_vector: i8, }",
  file "new_file.odin"}`. The file's `import` lines are kept too (`{file, ref, path}`).
  These types behave like the open file's own, by bare name (no import): Type menus (Fill > Type,
  Convert, `bit_set[●]`), the Struct literal list and its fields dot, member access (`Field of p`,
  hints `x   f32`), `Enum value` and switch cases, type-switch variants, aliases followed through
  loops, enumerated arrays and indexing, and a declaration `W :: Vec` in the open file reads as a
  type alias when `Vec` is a sibling's type or alias (test
  `test_sibling_alias_of_open_files_type`). Declarations inside a sibling's file-scope `when` block
  are found too (the scan uses `insertion_points`, which treats `when` bodies as file scope, and
  `decl_block_end` stays inside the `when`; read from the code, not test-pinned).
  Polymorphic structs are kept in `sibling_types` (kind `struct`, text `struct($T: typeid) {...}`).
  ```odin
  // main.odin: lucky_otter := ●  > Struct literal > point
  	lucky_otter := point{●}
  // fields dot lists: x   f32 | y   f32 | z   f32 | point_or_vector   i8
  ```
- **Rules & edge cases**:
  - Shadowing: the open file's file-scope declarations come first; a same-named type here hides the
    sibling's (`visible_sibling_type`, `own_declares`). Between siblings, the first file read
    (directory order) wins; within one file, the first declaration of a name wins.
  - `ident` resolution (`sibling_kind`, depth limit 8): `Vec :: point` is an `alias` if `point` is
    a type of the open file or (recursively) of any sibling, `proc_type` if it ends in a `#type
    proc`, and dropped if it names a constant or procedure (`Speed :: MAX_SPEED` is not a type),
    independent of file read order.
  - Package references inside sibling type text are rewritten from the sibling's point of view to
    the open file's (`sibling_type_here`): `strings.Builder` in a file that imports `core:strings`
    becomes `str.Builder` if the open file imports it as `str`, or `{expr "Builder", pkg
    "core:strings"}` (a type written inside that package, like a `CORE_FIELDS` row) if the open file
    doesn't import it, so fields and hints still resolve. Best effort for a mix (two different
    unimported packages, an unimported plus an imported one, or an unimported package plus a bare
    name this package declares, `map[point]linalg.Vector3f32`): references the open file imports
    are still renamed, the rest is kept as written, and the result is read as open-file text
    (`pkg ""`), e.g. `map[point]strings.Builder` -> `map[point]str.Builder`.
  - Read-only and index-free: no node index ever points into a sibling. A sibling's `Doc_Type` has
    `ni = -1` and `file` set; rename, go-to and data-member edits only touch the open file
    (docs/EDITOR_MODEL.md §3.4). Note: Doodle has **no go-to-definition feature** at all (no proc
    in src/model or src/app jumps the cursor to a declaration; the nearest thing is the read-only
    LT+Y docs panel, §12-13). EDITOR_MODEL.md's "go-to" is aspirational wording; a port that adds
    go-to-definition must open a sibling file read-only or switch files, never edit it in place.
  - Polymorphic structs (`Stack :: struct($T: typeid)`) are excluded from Struct literal.
- **Source**: siblings.odin (`scan_sibling_types`, `decl_text_from`, `decl_block_end`,
  `sibling_type`, `sibling_kind`, `visible_sibling_type`, `own_decl_names`, `sibling_type_rhs`,
  `sibling_type_here`, `brace_items`), data_types.odin (`doc_type_decls`, `Doc_Type`),
  data_member_edit.odin, ctrl.odin, branch.odin, var_types.odin consumers; tests in
  sibling_types_test.odin.

### 11. Sibling caching and limits

- **Trigger**: each `load_siblings` call.
- **Behavior**: per-file scans are cached in `App.sibling_cache` keyed by full path and compared by
  `size` and modification time. On a refresh, an unchanged file's cached scan is reused without
  reading it; a changed file is re-read and re-parsed; cache entries for files that disappeared or
  belong to another folder are freed. The open file is never scanned, but if it already has a cache
  entry (it was a sibling before) and its size and mtime are unchanged, that entry is kept for when
  it becomes a sibling again (a changed one is freed and not re-read while it is open). The App's
  flat lists (`sibling_procs`, `sibling_types`, `sibling_imports`) are rebuilt from the cache on
  every call. `load_siblings(app, "", "")` empties everything.
- **Rules & edge cases**: files larger than `SIBLING_MAX_BYTES = 1 << 20` (1 MiB) are skipped (both
  by directory size and by text length). Only `*.odin` files directly in the folder; directories
  and other extensions ignored. File name comparison with the open file is case-insensitive.
  `_test.odin` files and files for another OS are *not* excluded (see Open questions). After a
  refresh the capture-dot cache is invalidated (`g_app.capture_fp = 0`) because capture dots depend
  on what calls return.
- **Source**: siblings.odin (`load_siblings`, `take_cached_sibling`, `Sibling_File`,
  `free_siblings`); tests `test_load_siblings_reuses_unchanged_files`,
  `test_sibling_huge_source_skipped`, `test_load_sibling_procs_from_folder`.

### 12. LT+Y documentation panel: what is looked up

- **Trigger**: in the editor, hold LT and press Y (default layout: `BANK_LT.Y = .Docs`, HUD label
  `Docs`, glyph `?`, hint "documentation of the highlighted part"; remappable, 03). The model only
  raises a `.Docs` request; the app layer opens the panel (model.odin `keymap_run` ->
  app `app_requests` -> `doc_panel_open`).
- **Behavior** (docs.odin `doc_query`): works out a `Doc_Query{name, path, keyword, near}` from the
  highlighted part (the RT tree selection if one is sticky, else the cursor's leaf; 02):
  - on the purple attribute dot: keyword `attributes`;
  - on a dot (slot): the type it expects (its hint, else the unit's expected type), reduced to a
    base name by stripping `^`, `..`, `#soa`, `#simd`, `#sparse`, `distinct`, `[N]`, `[]`,
    `map[K]` (`^[]win.RECT -> win.RECT`, `map[string]int -> int`), e.g. `^testing.T ->
    {T, core:testing}`;
  - on a non-editable keyword/directive/attribute/calling-convention field: a `KEYWORD_DOCS` key
    (`else if`/`else` -> `if`; `else when` -> `when`; `=`, `:=`, `+=` ... -> `assignment`;
    `cast(` -> `cast`; `"c"` -> `calling convention`; `link_name="x"` -> `link_name`;
    `private="file"` -> `private`);
  - on a call's name: the name after the last `.` and the package its reference names
    (`fmt.println -> {println, core:fmt}`);
  - otherwise the first name in the part: `win.MB_OK -> {MB_OK, core:sys/windows}`; `p.x -> p`
    (the variable); `&x -> x`; a literal (`5`, `"hi"`, `'a'`, `.North`, `true`, `false`, `nil`)
    -> the type expected there (`add(1, ...)` with `b: int` -> `int`); a keyword name -> keyword.
  - `near` = the saved-file line of the cursor's node, so the nearest declaration wins.
- **Rules & edge cases**: nothing to look up (a file-scope green dot, a dot with no known expected
  type such as a green statement dot, a literal whose slot type is unknown, an empty leaf; also any
  model state other than `.Editor`): the panel does not open and the status line says `Nothing to
  look up here (highlight a name, call, type or keyword)`. A qualified type whose reference is not
  an import of this file (`foo.T` with no `foo` import) looks up `foo` itself. LT+Y only works in
  the editor: `keymap_run` raises the request, and `app_requests` opens at most one overlay per
  frame, `Docs` first.
- **Source**: docs.odin (`doc_query`, `type_query`, `base_type_text`, `first_name`,
  `import_path_of`, `keyword_key`, `is_keyword_name`), src/app/docs_panel.odin `doc_panel_open`,
  keymap.odin (`BANK_LT`, `.Docs`); tests `test_doc_query_parts`,
  `test_doc_query_dots_and_keywords`.

### 13. LT+Y documentation panel: the search chain and what is shown

- **Trigger**: follows feature 12.
- **Behavior** (docs.odin `lookup_doc(app, q, current_file, dir, root, os_name)`; `dir` = the open
  file's folder or the project folder; `root` = `odin_root()`; `os_name` = the running OS):
  - keyword query: the `KEYWORD_DOCS` entry (title = key, location `keyword` or `built-in`,
    "signature" = its example, doc = its text). The table has 91 entries: 52 keywords, directives
    and attributes (`if`, `for`, `in`, `switch`, `case`, `#partial`, `fallthrough`, `when`,
    `defer`, `return`, `break`, `continue`, `proc`, `struct`, `enum`, `union`, `bit_set`,
    `bit_field`, `map`, `distinct`, `using`, `cast`, `transmute`, `auto_cast`, `or_return`,
    `or_else`, `or_break`, `or_continue`, `context`, `import`, `package`, `foreign`, `where`,
    `#assert`, `#packed`, `#raw_union`, `#align`, `#reverse`, `#unroll`, `calling convention`,
    `assignment`, `attributes`, `test`, `private`, `export`, `init`, `fini`, `require_results`,
    `thread_local`, `link_name`, `deprecated`, `cold`) and 39 built-in types/procedures with
    `builtin = true` (`int` ... `conj`), written by hand.
  - no package path (`q.path == ""`), in order:
    1. **this file**, from the *live document* (`doc_to_source`, not the disk copy): `find_decl`
       with `near` and locals: the nearest declaration at or above the cursor line wins (locals and
       parameters shadow file scope); one below the cursor only if nothing is above; ties go to the
       less indented. Location `this file, line N`.
    2. **the other files of the folder** (the disk copy of the open file is skipped).
    3. **base:builtin** (`<root>/base/builtin`); since that file has almost no comments, when the
       found comment is empty or a single word (a section header like `// Procedures`), the
       `KEYWORD_DOCS` text of a built-in row (`builtin = true`) with that name replaces it, or the
       comment is dropped if there is none (`with_type_doc`). A multi-word or multi-line comment
       is kept.
    4. **base:runtime's `@builtin` procedures**: only files whose name starts with `core_builtin`,
       and only declarations with a `@builtin`/`@(builtin)` attribute above (`make` is found in
       `core_builtin.odin`).
    5. a keyword with that name (`keyword_key`, which also matches the built-in rows); else
       **not found**.
  - with a package path: the package folder (`package_dir`: `core:`/`base:`/`vendor:`/`shared:` ->
    `<root>/<collection>/<rest>`; a relative path like `../model` -> joined to `dir`; any other
    collection -> none), title `<alias_default(path)>.<name>` (`fmt.println`; note `win.MB_OK` is
    titled `windows.MB_OK`, from the path, not the document's alias; `vendor:lua/5.4` gives `lua.`).
    Not found there gives location `not found in <path>`; there is no fallback to this file or the
    built-ins for a qualified name.
  - Folder search (`lookup_in_dir`): reads every `.odin` file directly in the folder (directory
    order), skips files not containing the name as a substring, finds the least-indented
    declaration in the file (`find_decl` with no cursor: `name ::`, `name :=`, `name: T`,
    `a, name :: ...`; comment lines and `/* */` blocks skipped), and returns the first file that
    is compiled for `os_name` and is not `_test.odin`; files for another OS (`fmt_js.odin`,
    `#+build js`, `_linux_amd64`, `#+ignore`) *and `_test.odin` files* are only a fallback (the
    first such hit) when no other file declares it (`file_for_os`: an OS tag in either of the last
    two `_` parts of the file name; `build_matches`: comma = or, space = and, `!` = not, non-OS
    tokens such as `amd64` assumed true; tags, including legacy `//+build` / `//+ignore`, are read
    only before the `package` line). The OS tags known here are `windows linux darwin freebsd
    openbsd netbsd haiku essence freestanding js wasi orca` (so `_os`, `_posix`, `_unix` suffixes
    count as "any OS").
  - Content (`make_info`): `signature` = attribute lines directly above + the declaration
    (`decl_lines`): a procedure's header without its body (up to the body's `{`, or a `---`
    bodiless line, or the line where parens close not ending in `->`/`,`); a struct/enum/union/
    proc group with its whole body; otherwise until brackets balance; at most 40 lines then `...`;
    dedented to the declaration's indentation. `doc` = the comment block right above the first
    attribute line (`//` lines, or a `/* */` block, markers removed, common indentation removed,
    blank edge lines dropped, `//+` file-tag lines skipped; the comment must touch the declaration:
    a blank line between them means no doc), else a trailing `// comment` on the declaration line
    (`MAX :: 10 // (per level)` gives `(per level)` only when nothing is above). Location is
    `<path with forward slashes>:<line>` (1-based) for folder hits, `this file, line N` for the
    live document.
  - Not found: title in the error color, location `not found` or `not found in core:fmt`, body
    `No declaration found for it here, in this folder, or in the built-ins.`
- **Panel UI** (src/app/docs_panel.odin): a veil over the editor, a centered panel (width
  `min(screen - 80, 1100)`, above the HUD). Header: title (accent color, or error color when not
  found), location (dim), and at the right `Up/Down scroll   B close`. Body: the signature rows in
  the code font on a shaded background, wrapped to the panel, a small gap, then the comment in the
  UI font; tabs shown as 4 spaces; `(no comment above the declaration)` only when there is neither
  signature nor comment. `^`/`v` markers show more above/below. The panel owns all input: D-pad Up/
  Down scroll one row, Left/Right one page (rows that fit minus one); B, A, Y (and keyboard
  confirm/cancel) close it. Nothing in the document changes.
- **Rules & edge cases**: the lookup reads files synchronously when LT+Y is pressed (no index). The
  Odin root comes from `model.odin_root()`, a different search than the compiler finder used by
  check/run (see Open questions).

### 14. Background `odin check` and problem highlighting

- **Trigger**: automatic while the editor (or a menu over it) is shown: `check_tick` runs every
  frame when `m.state` is `.Editor` or `.Radial` (src/app/main.odin).
- **Behavior** (src/app/checker.odin):
  - Every `CHECK_POLL = 0.3` s it serializes the document as it would be saved (`doc_to_source`).
    If the text changed since the last poll, it records the time and waits. Once the text has been
    unchanged for `CHECK_DEBOUNCE = 0.6` s, no check is running, the document is non-empty, and this
    exact text hasn't been checked yet, it starts a check on a worker thread.
  - The worker builds a *scratch copy of the package*: `<temp>/doodle_check/` is emptied of
    `.odin`/`.txt` files, every `.odin` file of the open file's folder (the project folder for an
    unsaved document) except the open file (name compared case-insensitively) is copied there
    (including `_test.odin` files; no size limit), and the live document is written under
    the open file's base name (`main.odin` when unsaved). It then runs
    `odin check <scratch> -no-entry-point` with stdout+stderr redirected to
    `_check_output.txt` (Windows: through `cmd /c` with the outer-quote dance
    `""odin.exe" check "dir" -no-entry-point > "out" 2>&1"`; elsewhere `sh` with POSIX quoting)
    and reads the output back. The compiler is found by `odin_exe()` (src/app/shell.odin:
    `$ODIN_DIR`, `$ODIN_ROOT`, `toolchain/odin` next to Doodle or one level up, Settings > Setup's
    install folder, `C:\Odin` or `~/odin`, `~/Odin`, `/opt/odin`; else plain `odin` on PATH).
  - When the thread finishes, `parse_check_output` keeps only lines of the form
    `<path>.odin(<line>:<col>) <rest>` whose file *base name* equals the open file's
    (case-insensitive; `/` and `\` both accepted as separators). `Error:` is stripped,
    `Syntax Error:` becomes the prefix `Syntax: `, `Warning:` becomes `Warning: `, any other text
    after `)` is kept as is. Continuation lines (the echoed source and caret) are ignored because
    they contain no `.odin(`.
    Each problem is `{line, col, msg}` in saved-file coordinates, stored with the exact source text
    it was computed for.
  - Mapping back to the document: `node_line_starts` gives the saved-file line each node starts on
    (a node can span several saved lines: a long call saved one argument per line, 01/10);
    `node_for_line` finds the node covering a problem's line.
  - Display (src/app/editor_view.odin): every node with a problem gets a translucent red background
    over all its rows and a 3 px red bar at its left; gutter line numbers that carry a problem are
    drawn in the error color. When the cursor is on a field of such a node (not on a green dot or
    the purple attribute dot), a box at the right edge (width `min(500, 40% of screen)`, pale red
    with a red outline), just below the line and kept inside the code area, lists each problem of
    that node as `line L:C  message`, wrapped, separated by blank lines. The editor's title bar
    shows, right after the file name, `1 problem` / `N problems` in the error color whenever there
    are current problems (editor_view.odin; the count includes problems whose line maps to no node,
    which are otherwise not drawn).
  - Staleness: problems are shown only while the current text equals the text they were computed
    for (`current_diags`); within one poll (0.3 s) after any edit they disappear until the next
    check completes. Undoing back to exactly the checked text brings them back without a new check.
    A new check is not started for text equal to the last *completed* check's text.
- **Rules & edge cases**: one check at a time (a new one starts only after the previous thread is
  joined); the check never blocks the UI thread; on exit `check_shutdown` joins a running check and
  frees everything. Problems in other files of the package are discarded. If the compiler is
  missing, the shell's error text has no `.odin(` lines, so no problems are shown (silent). The
  checker never edits the document, never saves, and never touches the real project folder.
  Problem highlighting does not need a C toolchain (README platform table).
- **Source**: src/app/checker.odin (`Check_Job`, `check_tick`, `run_check`, `current_diags`,
  `check_shutdown`, `CHECK_DEBOUNCE`, `CHECK_POLL`), diagnostics.odin (`Diag`,
  `parse_check_output`, `node_line_starts`, `node_for_line`, `free_diags`), editor_view.odin
  (`draw_error_panel`, node shading in `draw_editor`); tests `test_parse_check_output`,
  `test_node_line_starts`.

### 15. Vendor shared libraries found before Run

- **Trigger**: any Run (Run list, RB favorite, LB tests; 09). After saving and after the Linux stb
  gate (`stb_run`, 09), `vendor_run(cmd, dir, keep_open)` runs.
- **Behavior**:
  - `vendor_needs(project_dir)` reads every `.odin` file directly in the *project* folder (the run's
    working folder `g_project_dir`, or `.`; not the open file's folder if that differs; the files as
    saved, since a Run saves first) and collects the distinct `vendor:...` import paths
    (`vendor_imports`: trimmed lines starting with `import `, the quoted path, so a `//`
    commented-out import doesn't count; an import inside a `/* */` block would). For each, the
    folder `<odin>/vendor/<rest>` (`vendor_lib_dir`, with `odin_dir()` from shell.odin) is listed;
    files that are shared libraries on this OS (`.dll`; `.so` or containing `.so.`; `.dylib`, any
    case — `is_shared_lib`) are the needs. A package with none (a static or system library) needs
    nothing. If `odin_dir()` finds no install (Odin only reachable through `PATH`), the check is
    skipped entirely and the run starts unprompted.
  - A need is *found* if its folder is already on the search path (Windows: the user PATH in
    `HKCU\Environment\Path`, read fresh because Doodle's own environment may be older, or Doodle's
    PATH; Linux/macOS: `LD_LIBRARY_PATH`/`DYLD_LIBRARY_PATH` or a non-comment line in `~/.profile`
    naming both the variable and the folder), or if every library file exists in the project folder
    or in a searched folder (Windows: PATH + user PATH entries; Linux: the variable's entries plus
    `/lib`, `/usr/lib`, `/usr/local/lib`, `/lib64`, `/usr/lib64` and the x86_64/aarch64 multiarch
    folders; macOS: `/usr/local/lib`, `/opt/homebrew/lib`, `/usr/lib`).
  - If nothing is missing (or every missing folder was waved through this session), the run starts
    at once with *all* needed folders prepended to the run's PATH (Windows) or library path.
  - Otherwise a full-screen prompt owns input: title `LIBRARY NOT ON YOUR PATH` (Linux/macOS:
    `LIBRARY NOT ON YOUR LIBRARY PATH`); one line per missing vendor package: `vendor:sdl3 needs
    SDL3.dll - it's in C:\Odin\vendor\sdl3, which the system can't find yet.` (several library
    files of one package are joined with `, `); then `Doodle adds it for this run either way. Added
    for good, the program also runs outside Doodle.`; three choices, D-pad Up/Down wrapping, A (or
    keyboard confirm) to choose, B (or keyboard cancel) = Cancel, Left/Right ignored; footer
    `D-pad move   A choose   B cancel`:
    1. `Add to my PATH (permanently)` (Windows) / `Add to my library path (~/.profile)` (others):
       Windows appends the folder to the user PATH registry value (keeps `REG_EXPAND_SZ`, `%VARS%`
       unexpanded) and broadcasts `WM_SETTINGCHANGE "Environment"` (2 s timeout); others append
       `export LD_LIBRARY_PATH="<dir>${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"  # added by Doodle for
       vendor:sdl3` to `~/.profile` (adding a newline first if the file doesn't end with one).
       Then the run starts; the status line shows the per-folder results joined with `; `
       (`added <dir> to your PATH (new terminals and programs see it)`, `<dir> is already on your
       PATH`, `couldn't change your PATH`; `added <dir> to ~/.profile (applies from your next
       login)`, `<dir> is already in ~/.profile`, `no home folder to add it to`, `couldn't write
       ~/.profile`).
    2. `Just this run`: the run starts; those folders are not asked about again until Doodle
       restarts.
    3. `Cancel`: nothing runs; status `run cancelled`.
- **Rules & edge cases**: the run always gets the folders on its own PATH, because a changed user
  PATH reaches only programs started after the change and Doodle started before. A trace replay
  never changes PATH or `~/.profile` (status `replay: PATH left as it is` / `replay: ~/.profile
  left as it is`; 11). Path comparison on Windows ignores case, `/` vs `\` and a trailing
  separator; on Linux it is case-sensitive. `System32` is not in the Windows search list.
- **Source**: vendor_libs.odin (`vendor_imports`, `vendor_lib_dir`, `is_shared_lib`,
  `path_list_has`, `path_list_add`, `profile_line`, `profile_has_dir`, `lib_path_var`),
  src/app/vendor_path.odin (`vendor_needs`, `vendor_run`, `handle_vendor_prompt_input`,
  `draw_vendor_prompt`, `VP_CHOICES`), vendor_path_windows.odin, vendor_path_other.odin
  (`lib_dir_on_path`, `lib_search_dirs`, `user_path_add`); tests in vendor_libs_test.odin.

## Invariants & constraints to carry forward

1. **HARD** — Library knowledge is static data generated offline from the toolchain install and
   checked in; it is never edited by hand ("AUTO-GENERATED ... do not edit") or at runtime, and
   consumers never free its strings.
2. **HARD** — Missing knowledge never blocks the user. An unknown procedure gets `req 0` +
   a repeating args dot; an unparseable signature is `(0, variadic, "", "?")`; a type that can't be
   resolved is `Unknown` and is never grayed out; a constant of kind `"?"` fits any slot; a package
   without table rows still offers `Other (name it yourself)`.
3. **HARD** — Conflicting information is merged permissively, never guessed narrowly: same name
   with different arities -> minimum `req`, variadic, no params, `ret "?"` (generator
   `resolve_sigs`, model `call_signature`).
4. **HARD** — The generator's required-argument counting must mirror the model's (`param_arity` in
   gen_core_procs.py and calls.odin: grouped names each count, a default = optional, `..T` or
   `#c_vararg` = variadic), so table rows and in-file procedures produce the same dots. (Enforced
   only by the "Mirrors ..." comments in both files; no test compares the two implementations.
   A port should share one implementation between generator and runtime.)
5. **HARD** — Argument dots equal the signature: one value dot per required parameter, typed with
   the parameter's declared type and the package it is written in; one repeating args dot if
   variadic; `(` `)` as two fields when there are no parameters (test
   `test_body_calls_category_import`).
6. **HARD** — Packages for another OS are hidden by tag at view time (`platform_ok` against the
   running OS); an empty tag means everywhere.
7. **HARD** — A package whose folder name is not an identifier is always inserted with an alias.
8. **HARD** — Import collections are listed in the order core, base, vendor, shared; `base:builtin`
   is never offered.
9. **HARD** — Large-list grouping is computed from the package's full name list; names used in the
   file are pinned on top and removed from the groups, so group shapes and labels do not depend on
   the file (heat stability).
10. **HARD** — Sibling files are read-only. Only names and declaration text are kept; no node index
    points into a sibling (`Doc_Type.ni == -1` for sibling types).
11. **HARD** — Visibility follows the language: across packages, anything private (`@(private)`,
    `#+private`) is invisible; within a package (siblings), only file-private
    (`@(private="file")`, `#+private file`) is invisible.
12. **HARD** — The open file shadows its siblings: its own declaration of a name wins.
13. **HARD** — Sibling loading is never on the per-frame path: only on open, save and folder change;
    unchanged files (same path, size, mtime) are not re-read; files over 1 MiB are skipped.
14. **HARD** — Sibling type text is interpreted with the sibling file's imports, translated to the
    open file's references (`sibling_type_here`).
15. **HARD** — Compiler problems are shown only for the open file and only while the document text
    equals the text they were computed for.
16. **HARD** — The compile check never blocks the UI and never writes into the project: worker
    thread, one at a time, after a 0.6 s quiet period, in a scratch copy.
17. **HARD** — Problem positions are saved-file lines and are mapped back to nodes through
    `node_line_starts` (one node may span several saved lines).
18. **HARD** — Docs for "this file" are read from the live document, not the disk copy; the nearest
    declaration at or above the cursor wins.
19. **HARD** — Docs prefer files compiled for the running OS; other-OS files are only a fallback.
20. **HARD** — Before a Run the program always receives the needed library folders on its own path,
    whatever the user picks (except Cancel); a trace replay never changes the user's PATH/profile.
21. **SOFT** — Windows is the reference platform for generated tables (Windows variants win).
22. **SOFT** — No language server: everything is local, synchronous where cheap, threaded where
    slow, and works offline.
23. **SOFT** — Menus stay d-pad sized: at most `FLAT_MAX = 60` entries flat, otherwise split by
    file, foreign block, shared prefix (3+), then 12-item alphabetical buckets.

## Data model & formats

Generated rows (all strings static):

- `CoreRow { depth: int, label: string, path: string, platform: string, dim: bool }` — one Import
  tree node; `depth` 0 = top of the collection; `path` empty for a pure group; `platform` empty or a
  comma list of `windows`, `linux`, `darwin`, `freebsd`, `openbsd`, `netbsd`, `haiku`, `essence`,
  `wasi`, `js`, `orca`, `android`, `unix`; `dim` for `internals` groups and their members.
  Example: `{1, "import c", "core:c", "", false}`.
- `ImportName { path, name }` — `{"vendor:lua/5.4", "lua"}`.
- `CoreProc { path, file, block, name: string, req: int, variadic: bool, params, ret: string }` —
  `file` = source file stem (used as a menu group), `block` = foreign library name or `""`,
  `params` = normalized parameter text (`""` unknown), `ret` = return text (`""` none, `"?"`
  unknown). Example: `{"core:sys/windows", "user32", "user32", "MessageBoxW", 4, false,
  "hWnd: HWND, lpText: LPCWSTR, lpCaption: LPCWSTR, uType: UINT", "INT"}`.
- `CoreType { path, file, kind, name, target }` — `kind` in struct, enum, union, bit_set,
  bit_field, distinct, alias (baseline counts 5,877 / 2,765 / 47 / 300 / 37 / 1,848 / 3,383);
  `target` = aliased/distinct type text, a polymorphic parameter list, or the bit_set spelling.
  Example: `{"core:sys/windows", "types", "alias", "LPCWSTR", "wstring"}`.
- `CoreConst { path, file, name, kind }` — `{"core:sys/windows", "types", "TRUE", "BOOL"}`,
  `{"core:sys/windows", "types", "MB_OK", "#int"}`.
- `CoreField { path, type_name, name, type: string, using_field: bool }` — rows grouped per
  `(path, type_name)` in declaration order.
- `CoreEnumMember { path, type_name, name }`.
- `Builtin_Arity { name: string, req: int, variadic: bool, ret: string }` (hand-written).
- `Keyword_Doc { key, example, text: string, builtin: bool }` (hand-written, 91 rows).

Runtime structures:

- Menu `Entry` fields used here: `import_path` (an import leaf), `platform`, `dim`, `pinned`,
  `fill` (`__call_import_proc__`, `__call_import__`, `__call_this_pkg__`, `__type_import__`,
  `__const_import__`, `__lit_type__` for Struct literal leaves), `call_pkg` (import reference),
  `call_name`, `ret`/`ret_pkg` (return type, or a constant's kind, and the package it's written
  in), `heat_key`, `alias` (set on the `Aliased import` group: entering it sets
  `app.import_alias`), `owned_label`.
- App fields: `add_menu` (built once, feature 2), `recent_imports` (most recent first), `os_name`
  (`"windows"`/`"linux"`/`"darwin"`, `""` elsewhere), `hint_pool` (interned hint strings read from
  document text; static table strings are not interned).
- `ImportRef { ref, path }` from `collect_imports` (alias or last segment; blank imports skipped).
- `Call_Sig { req, variadic, params: []Param, ret, pkg, known }`, `Param { name, type, optional,
  variadic }`.
- `Sibling_Proc { name, sig, file }`, `Sibling_Type { name, kind, text, file }` (kind: a type kind,
  `proc_type`, or `ident` pending resolution), `Sibling_Import { file, ref, path }`,
  `Sibling_File { path, size, mtime, procs, types, imports }`; App fields `sibling_procs`,
  `sibling_types`, `sibling_imports`, `sibling_cache` (kept across document resets; the folder
  outlives the document).
- `Doc_Query { name, path, keyword: bool, near: int }`, `Doc_Info { title, location, signature:
  []string, doc: []string, found }`.
- `Diag { line, col: int, msg: string }` (1-based, saved file), `Check_Job { src, file_name,
  project, odin_exe, output }`.
- `Lib_OS { Windows, Linux, Darwin }`, `Vendor_Need { import_path, dir, libs: []string, found }`.

External formats read or written:

- `odin check` text output: `C:/.../main.odin(5:27) Error: ...`, `...main.odin(7:1) Syntax Error:
  ...`, `...main.odin(L:C) Warning: ...`; continuation lines (echoed source, caret) start with a
  tab.
- `~/.profile` line: `export LD_LIBRARY_PATH="<dir>${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"  # added
  by Doodle for <import path>` (macOS uses `DYLD_LIBRARY_PATH`).
- Windows registry `HKCU\Environment\Path` (`REG_EXPAND_SZ` by default, `;`-separated).
- Scratch folder `<temp>/doodle_check/` with `_check_output.txt`.

## Carrying this to Rust

### (a) What transfers unchanged

- The principle that **menus are built from a local knowledge base**, not from free typing: every
  importable path, callable, type, constant, field and variant must be listable, with enough
  signature detail to create one typed dot per required argument.
- **Permissive unknowns** (invariant 2-3): unknown callee -> repeating args dot; unresolved type ->
  never grayed; an item the tables don't know still offers an "Other (name it yourself)" entry.
- **Menu sizing rules**: used-first pinning; `FLAT_MAX = 60`; split by source file/module, then by
  impl/extern block, then by shared name prefix (3+), then 12-item alphabetical buckets; grouping
  computed from the full list so it is stable across projects (heat).
- **Platform hiding** of modules/crates that don't build for the running target.
- **Sibling knowledge** as read-only, text-plus-name records, cached by path/size/mtime, never on
  the per-frame path, never holding node indices into other files; open file shadows others.
- **Docs panel** on LT+Y with the same query rules (call name -> its definition; a dot or literal
  -> the expected type; a keyword -> a keyword text), the same nearest-declaration rule, the same
  panel controls (Up/Down row, Left/Right page, B/A/Y close) and not-found wording.
- **Background check**: debounce (0.6 s quiet, 0.3 s poll), one at a time, off the UI thread, on a
  scratch copy, show only problems for the open file and only while fresh; red line shading + gutter
  numbers + a right-edge box on the cursor's line.
- **Pre-run library check** with the same three choices and the "always on the run's own path"
  rule.

### (b) Odin-specific pieces and their Rust analog

| Doodle (Odin) | Rust IDE |
|---|---|
| Collections `core:`/`base:`/`vendor:`/`shared:` scanned from the install | Roots of `use` paths: `std`, `core`, `alloc` (sysroot), the dependencies in `Cargo.toml` (resolved by `cargo metadata --format-version 1`), workspace member crates, and `crate::`/`self::`/`super::` modules. An "Add dependency" flow (crates.io sparse index `https://index.crates.io`, or `cargo add`) replaces "pick a vendor package" because a crate must be declared in Cargo.toml before `use`. |
| `package` = folder; siblings visible without import | crate = Cargo target (lib/bin/test/example); module = file reachable through `mod` declarations (`foo.rs` or `foo/mod.rs`). Items of other modules need a path or `use`, and Rust's default is **private**: an item is visible in its own module and descendants unless `pub`, `pub(crate)`, `pub(super)`, `pub(in path)`. The sibling feature becomes "the crate's module tree", with visibility computed per item; inserting a sibling item may also insert a `use`. Files not reachable from the crate root via `mod` are not compiled: flag them. |
| `@(private)` / `#+private` (importer-invisible), `@(private="file")` / `#+private file` (sibling-invisible) | `pub` levels above; `#[doc(hidden)]` items should also be left out of library menus (analog of `_name`). |
| `#+build`, file suffixes, `when ODIN_OS == ...` | `#[cfg(...)]`, `#[cfg_attr]`, `cfg!()`, target-specific dependencies; evaluate against `rustc --print cfg` for the target and the enabled Cargo features. Prefer "matches the current target" over Doodle's fixed "Windows wins". |
| Generated `CORE_*` tables from Python over Odin sources | rustdoc JSON (`--output-format json`, typed by the `rustdoc-types` crate): items with kinds module, function, struct (+fields, tuple fields), enum (+variants and their fields), union, trait (+items), impl (+items, trait, `for` type), constant, static, type alias, macro, proc-macro, re-export (`use`); `docs` (Markdown) and `attrs` per item; generics and where-clauses. Generate std tables at build time for the pinned toolchain (as Doodle embeds its tables) and dependency tables on demand, cached on disk keyed by crate name + version + enabled features + toolchain. Caveat: rustdoc JSON is an *unstable* output (`cargo +nightly rustdoc -- -Z unstable-options --output-format json`); std/core/alloc JSON is not buildable by cargo and ships as the `rust-docs-json` rustup component (`rustup component add --toolchain nightly rust-docs-json`, files under `<sysroot>/share/doc/rust/json/`), historically nightly-only; the format changes often (`FORMAT_VERSION`), so pin the `rustdoc-types` crate version to the pinned nightly. If a stable-only toolchain is required, fall back to rust-analyzer queries (or parse the sysroot sources with the same parser) to build the std table. |
| `req` / `variadic` / `params` / `ret` | Rust functions have fixed arity: `req` = number of inputs (minus `self` for method syntax); no defaults; "variadic" exists only for `extern "C"` C-variadic functions and for **macros** (`println!`, `vec!`, `format!`, `assert_eq!` ...) which need a hand-written arity table like `BUILTIN_PROCS`. `ret`: `()` = nothing, `!` = diverges; keep `"?"` for unresolvable `impl Trait`/associated types. |
| Proc groups | Traits and generics: a method can come from several traits; menu entries should be per (receiver type, method), with the trait shown and the needed `use Trait` inserted automatically if the trait is not in scope. |
| `CORE_FIELDS` with `using` flattening | Struct fields with per-field visibility (only visible fields listed); tuple structs (`.0`, `.1`); `Deref` targets add the target's fields and methods (auto-deref) — the analog of `using` promotion. `#[non_exhaustive]` structs can't be built with a literal outside their crate: gray out "Struct literal" with that reason. |
| `CORE_ENUM_MEMBERS` (`.North`) | Enum variants with data: unit `Dir::North`, tuple `Shape::Circle(●)`, struct `Shape::Rect { w: ●, h: ● }`; no implicit `.Member` selector (insert the path, or offer `use Dir::*`). |
| `CORE_CONSTS` kinds `#int`/`#float`/... (untyped) | Every Rust `const`/`static` has a declared type; fitting is "same type after aliases"; integer and float *literals* stay polymorphic (`{integer}` infers to the slot type). |
| `distinct T` / `A :: B` aliases | Newtype structs `struct Meters(f64);` / `type A = B;` |
| `bit_set[Enum]` | `bitflags!`/`enumset` types — macro-generated; the knowledge base must read the expansion (rustdoc JSON does list the generated consts and methods). |
| `odin check <dir> -no-entry-point` | `cargo check --message-format=json --all-targets` (add `--keep-going` if available); parse JSON lines with `"reason": "compiler-message"`: `message.level` (`error`, `warning`, `note`, `help`, `failure-note`), `message.message`, `message.code.code` (`E0308`), `message.spans[]` (`file_name` relative to the workspace root, `line_start`, `column_start`, `line_end`, `column_end`, `byte_start`, `byte_end`, `is_primary`, `label`, `suggested_replacement`, `suggestion_applicability`), `message.children[]`, `message.rendered`. Keep primary spans whose file is the open file; map `byte_start` straight to the syntax tree instead of lines. |
| Scratch copy `<temp>/doodle_check` | Rust compiles a whole crate (often a workspace) and can't take unsaved buffers: copy the workspace sources (excluding `target/`) to a persistent scratch directory, overwrite the open file with the live document, and run with a persistent scratch `CARGO_TARGET_DIR` so checks stay incremental. Or let rust-analyzer provide diagnostics for unsaved buffers (it does, natively) and keep `cargo check` as the authoritative "flycheck". Expect seconds, not milliseconds: cancel a running check when the text changes. |
| `vendor:` libraries needing `SDL3.dll` | `-sys` crates linking dynamic libraries: `cargo build --message-format=json` emits `"reason": "build-script-executed"` with `linked_libs` (`dylib=SDL2`) and `linked_paths` (`native=...`); look up `SDL2.dll` / `libSDL2.so*` / `libSDL2.dylib` in those paths and check PATH/`LD_LIBRARY_PATH` exactly like `vendor_needs`, then show the same prompt. |
| `ols` stub (unused) | rust-analyzer is mature and worth using as the type oracle (see (d)). |
| `KEYWORD_DOCS` (hand-written) | std documents keywords with `#[doc(keyword = "...")]` (the `std` "Keywords" pages: `fn`, `match`, `impl`, `where`, ...), but rustdoc JSON has no item kind for them (`rustdoc_types::ItemEnum` has no `Keyword` variant), so they are not in the JSON. Keep a hand-written keyword table as Doodle does (its text can be adapted from the std keyword pages' sources, `library/std/src/keyword_docs.rs`). Attribute docs (`#[derive]`, `#[cfg]`, `#[test]`, `#[inline]`, `#[must_use]`) need a hand-written table too. | `find_decl` line scan for LT+Y | Use the syntax tree / rust-analyzer "go to definition" + hover; for library items use the rustdoc `docs` Markdown and render it (code blocks in the code font). |

### (c) Rust concepts this area needs that Odin lacks

- **Methods and traits**: most of std's API is methods (`v.push(x)`, `s.len()`, `iter().map(...)`),
  not free functions. The knowledge base needs impl tables: (self type, generic params, trait or
  inherent, method name, receiver `self`/`&self`/`&mut self`, inputs, output). A "Call" menu on a
  value dot should offer "Method of `v`" grouped by trait (`Vec`, `Iterator`, `Clone`, ...),
  including blanket impls (`impl<T: Display> ToString for T`) — which is why a real trait solver
  (rust-analyzer) beats a table here.
- **Generics, lifetimes, `impl Trait`**: hints like `&'a str` or `impl AsRef<Path>` must be
  normalized for display and fitting (`&str` fits `impl AsRef<Path>`); unresolvable cases stay
  `Unknown` (never gray).
- **Ownership and borrows**: an argument dot of type `&mut Vec<T>` should offer `&mut x` forms; a
  by-value `String` param should offer `x.clone()` / `x.to_string()` when `x` is used later
  (rust-analyzer/borrow-checker diagnostics drive this).
- **Option/Result and `?`**: return-type knowledge enables "propagate with `?`" only when the
  enclosing fn returns a compatible `Result`/`Option` (analog of `or_return` gating).
- **Macros**: a built-in macro table (name, minimum args, variadic, first-arg-is-format-string) is
  the analog of `BUILTIN_PROCS`; user `macro_rules!` and proc macros from dependencies come from
  rustdoc JSON (macro items, derive macros), offered under "Macro" and in `#[derive(...)]` menus.
- **Modules and `use`**: inserting any external item must also ensure a `use` (or write the full
  path); conflicting names need `as` aliases (the analog of `IMPORT_NAMES` / aliased import).
- **Derives and attributes**: `#[derive(Debug, Clone, ...)]` options come from std's derivable
  traits plus derive macros found in dependencies; attribute docs for LT+Y.
- **Async**: `.await` offered only on `Future`-typed values inside `async` contexts; knowledge of
  which fns are `async` comes from the signature (`header.is_async` in rustdoc JSON).
- **Closures**: dots expecting `impl Fn(T) -> U` should offer a closure construct whose parameter
  dots are pre-typed from the bound.

### (d) Implementation advice

- **Parser**: use a real, error-tolerant parser for the open file and siblings (tree-sitter-rust,
  or `ra_ap_syntax` from rust-analyzer) instead of Doodle's line-based scans (`" :: proc"` at
  column 0, brace counting). Keep Doodle's rule that sibling parsing uses the same parser as the
  open file.
- **Type oracle**: run rust-analyzer as an LSP child process (or embed `ra_ap_ide`, accepting its
  unstable API) for: expected types at a position, hover/definition (LT+Y), method lists on a
  receiver (over LSP, `textDocument/completion` exposes rust-analyzer's ranking only through
  `sortText`; the explicit type-match flag is `CompletionRelevance::type_match` in the embedded
  `ra_ap_ide` API), diagnostics on
  unsaved buffers, and inlay type hints for capture dots. Keep a **local static table for std**
  (from rustdoc JSON) so menus open instantly and work before rust-analyzer finishes indexing; fall
  back to the table when RA is busy, exactly as Doodle falls back to "unknown".
- **Workspace model**: `cargo metadata` gives packages, targets, edition, features, dependency
  graph and source roots; watch `Cargo.toml`/`Cargo.lock` to invalidate the knowledge cache.
- **Generation pipeline**: write it in Rust (a `build.rs` or an `xtask`) using `rustdoc-types`;
  emit compact rows (`&'static str` tables via `include!` or a serialized blob loaded with
  `rkyv`/`bincode`) and build `HashMap<(&str, &str), Range<usize>>` indexes lazily with
  `std::sync::OnceLock`, as Doodle does with `sync.Once`.
- **Testing**: pin the tables like Doodle does (known std items with exact arity and return type,
  e.g. `Vec::with_capacity` req 1 ret `Vec<T>`; `std::fs::read_to_string` req 1 ret
  `io::Result<String>`), pin the diagnostics parser with captured `cargo check` JSON, and pin
  sibling/module visibility with in-memory sources (no disk), mirroring `scan_sibling_source`.
- **Threads**: `cargo check` and rust-analyzer requests on worker threads with channels; the model
  stays pure and testable with an abstract input (11).

## Open questions & known gaps

1. **Three Odin-root searches disagree.** Docs lookup and the `shared` listing use
   `model.odin_root()` (collections.odin: `$ODIN_ROOT`, PATH, else the constant `C:/Odin`, never
   `""`); check, run and vendor detection use `odin_dir()` in src/app/shell.odin (`$ODIN_DIR`,
   `$ODIN_ROOT`, bundled `toolchain/odin` next to the exe or one level up, Settings > Setup's
   install folder, `C:\Odin` / `~/odin`, `~/Odin`, `/opt/odin`; each only if the compiler exists
   there; `""` otherwise, and then `odin_exe()` falls back to plain `odin`); Settings > Setup, the
   stb build and the toolchain script use a third, app-level `odin_root()` (src/app/stb_build.odin:
   `odin_dir()`, else a `:`-split PATH search, else `""`). Doodle never sets `ODIN_ROOT`/`PATH` for
   itself, so (read from the code, not run): with Doodle's own Odin install on a Steam Deck and
   nothing on PATH, check works but LT+Y on `fmt.println` reports `not found in core:fmt` and
   `shared` is listed from `C:/Odin/shared` (so it shows the empty placeholder); conversely with
   Odin reachable only through PATH, check and run work (plain `odin`) but the vendor-library check
   (feature 15) is skipped. A port should have one toolchain locator.
2. **Generated tables are Windows-centric and unversioned.** No Odin version is recorded in them
   (Setup pins `ODIN_TAG dev-2026-11`); regenerating is manual. On Linux, vendor packages excluded
   for not building on Windows (vendor:x11/xlib, vendor:egl) appear in the Import tree (tag
   includes `linux`) but have no procedure/type rows, so they only offer "Other (name it
   yourself)".
3. **Per-OS files of core packages stay in the tables.** Rows are deduplicated by (path, file,
   block, name), so `core:fmt` has `println` in both `fmt_js` and `fmt_os`, and the `fmt` procedure
   menu shows a `fmt_js` file group on Windows.
4. **Multi-line `#type proc` targets are truncated** to their first line in `CORE_TYPES`
   (`Allocator_Proc` -> `"#type proc(allocator_data: rawptr, mode: Allocator_Mode,"`).
5. **Sibling scan gaps** (read from the code; no test pins these gaps): procedures
   are found only at column 0 with the exact substring `" :: proc"`, so those inside a sibling's
   file-scope `when` block, written `name::proc`, or declared `name :: #force_inline proc` are
   missed; proc groups are listed without a usable signature; `_test.odin` siblings and sibling
   files for another OS (`foo_linux.odin`) are included unfiltered (duplicate names: first wins).
6. **The scratch check copies only the flat folder** (read from the code, not run). Sub-packages
   and relative imports (`import "sub"`, `import "../lib"`) resolve relative to
   `<temp>/doodle_check` and will fail, producing spurious problems on the import lines. The scratch
   folder name is fixed, so two Doodle instances would race. `odin check` failing to start is
   silent.
7. **Problems in other files are dropped**, and there is no list/jump-to-next-problem feature: the
   title bar shows only the count (`N problems`), and a problem's text is visible only by moving
   the cursor onto a red line.
8. **The `shared` collection is scanned once per session** (lazy `ensure_menus`; verified that
   nothing resets `app.add_menu` on the editor's App), not on every menu open as
   docs/EDITOR_MODEL.md and the collections.odin header comment suggest.
9. **Docs lookup is linear and synchronous** (reads every file of a package folder on LT+Y), and
   `find_decl` is textual: a struct field `x: int` or a local can match before the intended
   declaration in folder searches (least indentation wins, but only within one file). The docs
   title uses the path's last segment, not the alias (`windows.MB_OK` for `win.MB_OK`).
10. **Dead code / stale docs**: `BUCKET_TARGET` is unused; `in_sibling_folder` in
    src/app/filenav.odin is defined but never called; src/lsp/lsp.odin is an unused stub and
    ARCHITECTURE.md §5.9 / docs/INSTALL.md §3 / docs/UX.md still describe ols integration.
11. **`System32` and the application folder** are not part of the Windows DLL search the vendor
    check performs, so a library installed only there triggers the prompt anyway.
12. **Built-in procedure list is hand-maintained** and can drift from the compiler's (e.g. new
    built-ins); `quaternion` is deliberately absent.
13. **Used-call detection is a substring scan** (`collect_called_procs`, feature 5): the first
    `ref.` on a line up to the next `(` is taken as a called name, which can pin a bogus entry
    (`MB_OK, bar` from `foo(win.MB_OK, bar())`) or match another identifier ending in the ref
    (`myfmt.` for `fmt`). A port should take "used names" from the syntax tree.
14. **Vendor detection looks only at the project folder** (`g_project_dir`, the run's working
    folder), not at the open file's folder if it differs, and only at saved files; an import inside
    a `/* */` block counts.
15. **Row counts and statistics in this doc are baseline values**: they change whenever the
    generators are rerun against a different Odin install, and nothing records which install
    produced the committed tables.
